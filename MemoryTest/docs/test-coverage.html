MemoryTest — Cobertura de testes e como replicar

Documento técnico de referência. Lista todos os testes que o MemoryTest executa, qual dado cada um lê do device, quais permissões precisa e como replicar a mesma lógica em outro projeto.

Visão geral

O MemoryTest é um conjunto de testes de fábrica que valida RAM e storage (eMMC/UFS) de tablets/celulares antes de ir a campo. Detecta defeitos via:

  • memtester — exercício de padrões em RAM com mlock.
  • Health registers do chip de storage (life_time, pre_eol_info) — lidos do sysfs.
  • I/O test — write/read de 512 MB com integridade via md5.
  • Kernel log — busca de erros de hardware no dmesg.
  • getprop — identificação do device.
Saída do teste

Cada execução produz memtest_full_<timestamp>.log (factory) ou ram_deep_<timestamp>.log (deep) + um result.txt chave=valor. Status final: PASS ou FAIL com lista de razões.

Modos de teste — Factory × Deep

O projeto tem 2 scripts independentes, cada um com seu escopo. Não são variações de um mesmo teste — fazem coisas diferentes.

Quando usar cada um
  • Factory: cada device antes de sair pra cliente. Linha de produção, decisão PASS/FAIL rápida, cobertura ampla mas rasa.
  • Deep RAM: device que veio com queixa, ou validação de lote/homologação. Cobertura profunda de RAM, sem mexer em storage.

Os 2 são independentes. Você pode rodar Deep depois do Factory (ou vice-versa) sem conflito — usam mesmo workdir mas arquivos com nomes diferentes.

"Stress paralelo" foi removido

Versões antigas do deep tinham um stress paralelo com /dev/urandom rodando junto com o memtester. Foi removido porque virava teste de horas sem critério de parada. Hoje o deep é só memtester, mas com configuração mais pesada (mais MB, mais loops, mais tempo) que o quick. A cobertura extra vem da repetição dos 16 padrões em mais memória, não de stress externo.

Arquitetura — 2 caminhos vivos

CaminhoQuem rodaUID/ContextoQuando usar

Os scripts são idênticos, mas o ambiente de execução muda — isso gera diferenças de capacidade:

Pros 8 testes do projeto, num device userdebug + SELinux Permissive, a cobertura prática é equivalente porque os arquivos críticos (sysfs 0444, /proc/meminfo) são world-readable. Em produção (user + Enforcing), o APK platform_app é mais robusto.

Pré-requisitos AOSP

Pra o caminho APK funcionar 100% (com cobertura completa), o device precisa ter na árvore AOSP:

  1. PRODUCT_PACKAGES += memtester (em device.mk) — binário em /system/bin/memtester.
  2. PRODUCT_PACKAGES += MemoryTest — APK em /product/priv-app/MemoryTest/ (ou /system/priv-app/).
  3. SELinux Permissive:
    • SPRD/Qualcomm/genérico: BOARD_KERNEL_CMDLINE += androidboot.selinux=permissive
    • MTK MT6761: PRJ_SELINUX_STATUS := 2 no project file do LK — BOARD_KERNEL_CMDLINE é ignorado nesse SoC.
  4. APK declarado como android_app_import em Android.bp ou Android.mk com: 
    android_app_import {
    name: "MemoryTest",
    apk: "MemoryTest.apk",
    certificate: "platform",
    privileged: true,
    presigned: false,
}
Aprendizados importantes
  • APK como untrusted_app tem RLIMIT_MEMLOCK baixo (~8 MB) — memtester reduz pra esse tamanho e vira fake-fast PASS enganoso. Por isso a Opção 3 (platform_app) é necessária pra teste de RAM válido.
  • adb root em MTK + Windows quebra o adb-server. Em MTK preferir adb shell su 0 ou rebuild do AOSP com SELinux já permissive.

1. Device identification

APKScriptOnlysem rootfactory + deep

O que valida: identifica o device (modelo, fabricante, build, ABI, debuggable, fingerprint). Não tem critério de PASS/FAIL — é meta-info pro relatório.

Fonte de dados

getprop ro.serialno
getprop ro.product.model
getprop ro.product.brand
getprop ro.product.device
getprop ro.product.board
getprop ro.product.cpu.abi
getprop ro.hardware
getprop ro.soc.manufacturer
getprop ro.build.version.release
getprop ro.build.fingerprint
getprop ro.build.type           # user / userdebug / eng
getprop ro.debuggable           # 0 / 1

Permissão

Nenhuma. getprop é acessível por qualquer UID.

Observações por vendor

  • MTK MT6761: ro.soc.manufacturer retorna vazio. Usar ro.hardware (ex: mt6761) ou ro.product.board (ex: k61v1_32_bsp_1g) pra identificar SoC.

2. Storage identification (vendor/modelo)

APKScriptOnlysem rootdepende do kernel

O que valida: identifica vendor e modelo do chip de memória (eMMC ou UFS). Importante pra rastreabilidade e correlação de defeitos em lote.

Detecção UFS (primeiro)

# procura health_descriptor no sysfs UFS
/sys/devices/platform/soc/*ufs*/health_descriptor
/sys/bus/platform/devices/*ufs*/health_descriptor

# depois lê:
<base>/string_descriptors/manufacturer_name    # vendor
<base>/string_descriptors/product_name         # modelo

Detecção MMC/eMMC (fallback)

# caminho clássico
/sys/class/mmc_host/mmc*/mmc*:*/cid             # CID em hex (16 bytes)
/sys/class/mmc_host/mmc*/mmc*:*/name            # PNM (ASCII)
/sys/class/mmc_host/mmc*/mmc*:*/manfid          # MID (vendor)

# parse manual do CID se sysfs não tiver name/manfid:
# bytes 1-2 do CID    = MID (manufacturer ID)
# bytes 5-14 do CID   = PNM em hex (decode ASCII)

MID conhecidos (eMMC)

MIDVendor
0x15Samsung
0x90SK Hynix
0x70Kingston
0x11Toshiba/Kioxia
0x13Micron

Permissão

Sysfs 0444 (world-readable) em devices testados. Funciona como uid shell e como platform_app.

3. Storage health (LifeTime + Pre-EOL)

APKScriptOnlysem rootdepende do driver

O que valida: estimativa de desgaste do chip eMMC/UFS (LifeTime A/B) e proximidade do fim de vida útil (Pre-EOL). Lido do EXT_CSD do eMMC ou do Device Descriptor do UFS, exposto pelo driver kernel no sysfs.

Interpretação dos valores

Valor (hex)LifeTime A/B (% usado)Pre-EOL
0x00não definido—
0x010–10%Normal
0x0210–20%Warning (~80%)
0x0320–30%Crítico (esgotado)
...(+10% por nível)—
0x0A90–100%—
0x0Bexcedido—

UFS

<health_descriptor>/life_time_estimation_a
<health_descriptor>/life_time_estimation_b
<health_descriptor>/pre_eol_info

eMMC/MMC — múltiplos formatos (o script tenta na ordem)

  1. Arquivos separados (Samsung/Qualcomm/etc): 
    /sys/class/mmc_host/mmc0/mmc0:0001/life_time_type_a
/sys/class/mmc_host/mmc0/mmc0:0001/life_time_type_b
/sys/class/mmc_host/mmc0/mmc0:0001/life_time_estimation_a
/sys/class/mmc_host/mmc0/mmc0:0001/life_time_estimation_b
/sys/block/mmcblk*/device/life_time_type_a       # alguns kernels
  2. Arquivo único (Allwinner / MTK MT6761): 
    /sys/class/mmc_host/mmc0/mmc0:0001/life_time     # "0x01 0x01" (A e B separados por espaço)
    Parse: awk '{print $1}' pra A, awk '{print $2}' pra B.
  3. MTK fallback (alguns kernels MT676x antigos): 
    /proc/bootdevice/life_time_est_typ_a
/proc/bootdevice/life_time_est_typ_b
/proc/bootdevice/lifetimeA
/proc/bootdevice/lifetimeB
/proc/bootdevice/pre_eol_info

Limitação

Driver MMC pode não expor

O valor está sempre no chip (bytes 267-269 do EXT_CSD). Mas o driver MMC do kernel escolhe se cria os arquivos sysfs. Em alguns kernels MTK stock o driver não expõe. Alternativas (todas pesadas):

  • Compilar mmc-utils e rodar mmc extcsd read /dev/block/mmcblk0 — requer root (CAP_SYS_RAWIO no ioctl).
  • Patchar o driver MMC do kernel.
  • Aceitar N/A e usar só Pre-EOL como termômetro.

4. Storage capacidade

APKScriptOnlysem rootfactory only

O que valida: tamanho total do storage. Comparado com expectedStorageGb do profile pra confirmar que o device tem a memória que devia ter.

Método primário

STOR_BLOCK=$(readlink -f /dev/block/by-name/userdata | sed 's/p[0-9]*$//')
blockdev --getsize64 "$STOR_BLOCK"      # bytes do device inteiro

Fallback

df /data | awk 'NR==2{print $2}'        # KB do /data (sub-estimado mas serve)

Permissão

blockdev --getsize64 em /dev/block/mmcblk0 tem permissão de leitura em shell/system. Se falhar (DAC mais restrito), cai no df.

5. RAM info

APKScriptOnlysem rootfactory + deep (expandido)

Deep RAM lê mais campos (MemFree, Buffers, Cached, SwapTotal, SwapFree) e gera dump completo de /proc/meminfo no log pra debug.

O que valida: RAM total física + RAM disponível pro processo. Compara MemTotal com expectedRamGb. MemAvailable é usado pra dimensionar o teste do memtester.

Fonte

grep MemTotal     /proc/meminfo | awk '{print $2}'   # KB
grep MemAvailable /proc/meminfo | awk '{print $2}'   # KB

LPDDR type (best-effort)

getprop ro.boot.ddr_type
getprop ro.boot.dram_type
getprop vendor.boot.ddr_type
cat /proc/bootdevice/dram_type      # MTK fallback
LPDDR type frequentemente N/A

O bootloader é quem deveria popular essa property. Em muitos vendors (MTK MT6761 inclusive) ela vem vazia. Documenta-se como limitação — não invalida o teste de RAM.

Permissão

Nenhuma. /proc/meminfo é world-readable.

6. Storage I/O test (dd)

APKScriptOnlysem rootroot opcional

O que valida: (1) write throughput, (2) read throughput, (3) integridade dos dados (md5 antes/depois). Falha se velocidade abaixo do threshold ou hash diverge.

Comandos

cd /data/data/<package>/files/memtest_work   # ou /data/local/tmp/memtest_work no ScriptOnly

# Write
T1=$(date +%s%3N)
dd if=/dev/urandom of=testfile bs=4M count=128 conv=fsync
T2=$(date +%s%3N)
WRITE_MS=$((T2-T1))
WRITE_MBPS=$(( 512 * 1000 / WRITE_MS ))

md5sum testfile > hash_before.txt

sync
echo 3 > /proc/sys/vm/drop_caches            # PRECISA UID 0; se falhar, cosmetico

# Read
T3=$(date +%s%3N)
dd if=testfile of=/dev/null bs=4M
T4=$(date +%s%3N)
READ_MS=$((T4-T3))
READ_MBPS=$(( 512 * 1000 / READ_MS ))

md5sum testfile > hash_after.txt
diff hash_before.txt hash_after.txt

Thresholds (do profile)

  • MIN_WRITE_MBPS — depende da classe (eMMC 4.5/5.0/5.1, UFS 2.x/3.x).
  • MIN_READ_MBPS — idem.
  • STORAGE_TEST_SIZE_MB — default 512 MB. Reduzir em devices com pouco espaço livre.

Permissão

OperaçãoPermissão
dd if=/dev/urandomworld-readable
escrever em filesDir ou /data/local/tmpuid do APK ou shell
echo 3 > /proc/sys/vm/drop_cachesuid 0 obrigatório. Se falhar, é cosmético (read pode vir cacheado, mas teste continua).

Por que sem root o read pode vir "rápido demais"

Sem drop_caches, o read pode vir do page cache em RAM em vez do storage. Mitigação: tamanho do teste > cache disponível (512 MB > cache em devices com 1–4 GB de RAM funciona na prática).

7. RAM test (memtester)

APKScriptOnlysem rootmlock unlimited crítico

O que valida: o teste mais crítico — exercita células de RAM com 16 padrões diferentes. Detecta stuck-at, coupling faults, decoder faults, pattern-sensitive bugs.

Binário

Procura nos caminhos:

/system/bin/memtester          # padrão se empacotado via AOSP
/system/xbin/memtester
/vendor/bin/memtester
/data/local/tmp/memtester      # ScriptOnly empurra via adb push

Execução

memtester <SIZE>M <LOOPS>

# Exemplo factory (quick):
# SIZE = min(50% MemAvailable, QUICK_MEMTEST_MAX_MB)
# LOOPS = 1
# TIMEOUT = 600s

Padrões executados (16 por loop)

Stuck Address, Random Value, Compare XOR/SUB/MUL/DIV/OR/AND, Sequential Increment, Solid Bits, Block Sequential, Checkerboard, Bit Spread, Bit Flip, Walking Ones, Walking Zeroes.

Por que mlock é crítico

RLIMIT_MEMLOCK baixo = fake-fast PASS

O memtester chama mlock() pra travar a memória alocada e impedir swap/paging. Se o limite for baixo (típico de untrusted_app: ~8 MB), o memtester reduz o teste pra esse valor e termina em segundos com PASS — mas testou só 8 MB.

Por isso o APK precisa rodar como platform_app (priv-app + platform key), que tem RLIMIT_MEMLOCK=unlimited.

Cobertura

  • Quick (factory line): ~50% do MemAvailable, 1 loop, ~3 min. Pega ~75% dos defeitos comuns.
  • Deep (bancada/RMA): ~70% do MemAvailable, 2–3 loops, ~30 min. Cobertura maior.

Por que nunca 100%

Não dá pra testar a RAM que o próprio Android está usando (kernel, zygote, system_server). Em 1 GB de RAM, ~520 MB ficam ocupados pelo sistema, restando ~340 MB testáveis sem OOM. Pra 100% precisa teste offline (memtest86+ no bootloader).

8. Kernel log analysis (dmesg)

APKScriptOnlysem root preferível

O que valida: busca padrões de erro de hardware no kernel log. Pega panics, ECC errors, I/O errors, uncorrectable bits, bad blocks — sinais de RAM/storage defeituoso vistos pelo kernel.

Comando

dmesg > dmesg.txt 2>/dev/null

grep -iE "I/O error|ufs error|mmc error|memory corruption|hardware error|ecc error|bad block|uncorrectable|panic" dmesg.txt

Permissão

Android versionRestrição
até Android 9dmesg acessível pra shell
Android 10+dmesg_restrict pode estar habilitado — só root lê. Em SELinux Permissive, retorna o conteúdo mas shell/system precisa de capability

Se dmesg.txt vier vazio, o script reporta "dmesg: não disponível" mas não falha o teste — análise é cosmética.

Deep RAM Diagnostic — visão

O deep é um script separado (ram_diagnostic_deep_verbose_root_exec.sh) focado exclusivamente em RAM. Não toca em storage, não roda dd test, não verifica health. Existe pra aprofundar a investigação em devices que passaram pelo factory test e ainda parecem suspeitos, ou pra homologação de lote.

Quando rodar Deep
  • Device veio com queixa de "trava sozinho", "reinicia", "tela vira preta" → roda Deep RAM.
  • Validação de homologação de novo lote de chips → Deep RAM por amostragem.
  • Confirmação de defeito antes de abrir RMA com fornecedor.

Deep — RAM info expandida

APKScriptOnlysem root

O que valida: snapshot completo do estado de memória. Inclui swap (quase sempre 0 em Android, mas registra), buffers e cache pra correlacionar com uso real.

Campos lidos

grep MemTotal     /proc/meminfo    # KB total
grep MemAvailable /proc/meminfo    # KB disponível pra alocar
grep MemFree      /proc/meminfo    # KB livre (sem buffers/cache)
grep '^Buffers:'  /proc/meminfo    # KB em buffers de I/O
grep '^Cached:'   /proc/meminfo    # KB em page cache
grep SwapTotal    /proc/meminfo    # KB swap total (geralmente 0)
grep SwapFree     /proc/meminfo    # KB swap livre

Dump completo

Além dos campos acima, o script faz cat /proc/meminfo inteiro e anexa no log — útil pra correlacionar Slab, KernelStack, PageTables, etc, depois do teste.

Permissão

Nenhuma. /proc/meminfo é world-readable. Funciona em qualquer UID.

Deep — Memtester profundo

APKScriptOnlyroot preferívelmlock unlimited crítico

O que valida: mesmo memtester do factory, mas com configuração muito mais agressiva. Não é stress paralelo — é o memtester clássico (16 padrões) rodando mais vezes em mais memória.

Defaults do deep

VariávelFactory (quick)Deep
MEMTEST_PERCENT40–50%60%
MEMTEST_MAX_MB5122048
MEMTEST_LOOPS13
MEMTEST_TIMEOUT_S600 (10 min)3600 (1 h)
MIN_MEMTEST_MB128128

Execução com progresso periódico

sync
echo 3 > /proc/sys/vm/drop_caches      # se root, limpa caches antes
memtester <SIZE>M <LOOPS> > ram_deep_memtester.log 2>&1 &

# Polling: a cada 15s reporta tempo decorrido
# A cada 60s faz tail das últimas 30 linhas pro log principal
# Se passar do timeout: kill normal → 2s → kill -9 → marca FAIL

Critério de FAIL

  • Exit code do memtester ≠ 0
  • Linha contendo FAILURE no output do memtester
  • Timeout (1h por default) — encerra com SIGKILL e marca FAIL

Por que mais loops

Cada loop dos 16 padrões testa as MESMAS células alocadas. Defeitos intermitentes (timing, retenção, térmicos) podem só aparecer na 2ª ou 3ª passagem, quando o chip já está aquecido. 1 loop pega ~75% dos defeitos; 3 loops pega ~90%.

Deep — dmesg patterns focados em RAM

APKScriptOnlyroot preferível

O que valida: mesma análise dmesg do factory, mas com regex diferente — foca em eventos relacionados a RAM em vez de storage.

Patterns do deep

grep -iE "memory corruption|hardware error|ecc error|uncorrectable|panic|oom|out of memory|page allocation failure|bad page|kernel BUG"

vs Factory

grep -iE "I/O error|ufs error|mmc error|memory corruption|hardware error|ecc error|bad block|uncorrectable|panic"

O que cada termo significa

PatternIndica
memory corruptionRAM corrompendo dados
ecc errorErro corrigido (se houver ECC) — sinal precoce
uncorrectableErro não corrigível — RAM ou eMMC degradado
oom / out of memoryOOM killer — pode ser falta de RAM ou leak (não defeito de hardware)
page allocation failureKernel não conseguiu alocar — pressão extrema ou fragmentação
bad pagePágina com corruption detectada pelo kernel
kernel BUGAssertion failure no kernel — frequentemente disparado por RAM ruim
panicKernel parou — pode ter raiz em RAM

Se encontrar qualquer match, o teste vira FAIL e os matches vão pro log completo (até 20 linhas mostradas).

Deep — Root bootstrap agressivo

O que muda em relação ao factory: o deep tenta escalar pra root antes de qualquer coisa, porque precisa de drop_caches + dmesg + possivelmente acesso protegido. O factory virou best-effort (commit recente).

Fluxo do bootstrap

CURRENT_UID=$(id -u)

if [ "$CURRENT_UID" != "0" ]; then
    if [ "$RAM_DEEP_ALREADY_TRIED_ROOT" = "1" ]; then
        # 2ª tentativa falhou → loga ERRO e segue sem root
    else
        export RAM_DEEP_ALREADY_TRIED_ROOT=1
        if command -v su; then
            exec su 0 sh "$0" "$@"     # reexec como root
        fi
    fi
fi

Por que difere do factory

AspectoFactoryDeep
Sem su no PATHcontinua sem root (warning)continua sem root + ERROR no log
Workdir de logmemtest_work/cria memtest_work/ e escreve ram_deep_root_bootstrap.log antes do log principal
Re-execvia exec su 0 sh "$0"idem
Variável de guardaROOT_REEXEC_DONERAM_DEEP_ALREADY_TRIED_ROOT

Implicação prática

Pra rodar o deep com cobertura máxima:

  1. Build userdebug (que tem su em /system/xbin/su) — OU
  2. SELinux Permissive + APK como platform_app (pra ter as capabilities necessárias mesmo sem uid 0)

Em build user puro, o deep continua rodando mas algumas coisas falham silenciosamente (drop_caches, dmesg parcial).

SPRD (Spreadtrum/Unisoc) — TL10, T2070D

  • SELinux Permissive via BOARD_KERNEL_CMDLINE += androidboot.selinux=permissive funciona.
  • Sysfs eMMC expõe formato "separado" (life_time_type_a/b) ou life_time_estimation_a/b.
  • Sem /proc/bootdevice/ tipicamente.

MediaTek MT6761 — L400

  • BOARD_KERNEL_CMDLINE é ignorado — cmdline é montada pelo LK (Little Kernel) em runtime. Pra Permissive: PRJ_SELINUX_STATUS := 2 no project file do LK + rebuild/flash do lk.img.
  • Sysfs eMMC expõe formato "único": /sys/.../life_time com "A B" separados por espaço (estilo Allwinner).
  • Alguns kernels MTK têm /proc/bootdevice/life_time_est_typ_a/b e pre_eol_info — fallback adicional implementado.
  • ro.soc.manufacturer vazio.
  • ro.boot.ddr_type e similares vazios — LPDDR type fica N/A.
  • adb root em Windows quebra adb-server.

Thresholds & profiles

Cada SKU tem um <MODELO>.conf em profiles/ com:

MIN_WRITE_MBPS              # mín. write storage
MIN_READ_MBPS               # mín. read storage
STORAGE_TEST_SIZE_MB        # tamanho do teste I/O
EXPECTED_RAM_GB             # RAM esperada (gate de PASS)

QUICK_MEMTEST_PERCENT       # % do MemAvailable pro teste quick
QUICK_MEMTEST_MAX_MB        # teto
QUICK_MEMTEST_MIN_MB        # piso
QUICK_MEMTEST_LOOPS         # loops do memtester quick
QUICK_MEMTEST_TIMEOUT_S     # timeout

MEMTEST_PERCENT             # idem pra teste deep
MEMTEST_MAX_MB
MEMTEST_LOOPS
MEMTEST_TIMEOUT_S

No APK, esses valores ficam num DeviceProfile no Room database, baixados do servidor local ou usando o perfil Default(T2070D) embarcado.

Replicar em outro projeto

Caminho minimalista (só os scripts)

  1. Copie full_memtest.sh e ram_diagnostic_deep_verbose_root_exec.sh.
  2. Compile memtester pra ABI do device (arm32/arm64/x86) e empacote.
  3. Crie um wrapper que faça adb push dos scripts + binário e rode via adb shell.
  4. Crie profiles .conf com thresholds do SKU.

Caminho com APK (UI no device)

  1. Copie ScriptRunner.kt (extrai asset → ProcessBuilder("/system/bin/sh", scriptFile)).
  2. Embarque os scripts em assets/ do seu APK.
  3. Compile o APK e empacote como prebuilt no AOSP do device: 
    // Android.bp
android_app_import {
    name: "MeuTeste",
    apk: "MeuTeste.apk",
    certificate: "platform",
    privileged: true,
}
  4. Adicione PRODUCT_PACKAGES += MeuTeste memtester e o flag de SELinux Permissive no device.mk/BoardConfig.mk (ou LK no MTK).
  5. Rebuild + flash. O AOSP re-assina com a platform key automaticamente.

Validar a integração

Use o pre_check.sh do ScriptOnly como teste de capacidade — ele lista o que funciona e o que está bloqueado num device específico, sem alterar nada.

Princípio chave

Toda a lógica de teste fica nos scripts shell. APK e AOSP existem só pra dar permissões + UI. Isso permite mesma cobertura em qualquer device que tenha SELinux Permissive + memtester instalado.
