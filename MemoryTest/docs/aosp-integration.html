Integração AOSP — MemoryTest

Guia passo a passo — daemon como system_ext / coredomain

Versão do documento: 2.0 Público: engenheiros de plataforma / AOSP Pré-requisito: árvore AOSP buildable, build userdebug/eng

1. Arquitetura — por que precisa de daemon?

O APK MemoryTest roda no UID de aplicativo comum (untrusted_app) e não tem acesso ao su. Os scripts de teste, porém, precisam de root para ler life_time de UFS, escrever em /proc/sys/vm/drop_caches, ler /sys, etc.

A solução é um daemon nativo que inicia como root via init.rc, abre um socket Unix em /dev/socket/memtest_daemon, recebe comandos do APK, e exec os scripts com as variáveis de ambiente do device profile.

APK (untrusted_app, sem root) │ socket Unix /dev/socket/memtest_daemon ▼ memtest_daemon (root, coredomain, permissive) │ fork + setenv() + exec ▼ /system/bin/sh /system_ext/etc/factory/full_memtest.sh

1.1. Onde fica e por quê

ComponentePartiçãoDomínio SELinux
Daemon (memtest_daemon) /system_ext/bin/ memtest_daemon (coredomain, permissive)
Scripts /system_ext/etc/factory/ label default da partição
Workdir runtime /data/vendor/memtest/ label default (vendor_data_file)
APK /product/app/ (ou /system/app/) untrusted_app
Por que system_ext e não vendor? Em devices Treble (Android 10+), o AOSP tem um neverallow (system/sepolicy/public/domain.te:716) que bloqueia qualquer app conectar em sockets Unix de vendor domains. Foi a primeira tentativa e quebrou o build. Movendo o daemon para system_ext (que é parte de coredomain), apps e daemon ficam do mesmo lado da separação core/vendor — a regra não dispara.
Por que permissive memtest_daemon? O daemon precisa fazer várias operações privilegiadas (acessar /sys/class/scsi_device/, escrever em drop_caches, exec de shell, escrever logs em /data). Cada uma dessas combinações de domínio + tipo + permissão bate em algum neverallow do AOSP base se for expressa como allow explícito. Como a ferramenta só roda em userdebug/eng (controlado pelo init.rc: on property:ro.debuggable=1), declarar o domínio como permissive é a saída pragmática — o SELinux loga as violações em dmesg mas não bloqueia.

2. Pré-requisitos

  • Árvore AOSP clonada e capaz de buildar para o device alvo.
  • Build environment funcional: source build/envsetup.sh e lunch <target>.
  • Build do tipo userdebug ou eng — o daemon só inicia se ro.debuggable=1.
  • Pacote memtester precisa estar disponível na imagem (vide troubleshooting).
  • Algum diretório referenciado por SYSTEM_EXT_PRIVATE_SEPOLICY_DIRS (ou criar um novo).

2.1. Convenções deste guia

<aosp> = raiz da árvore AOSP do seu device. <vendor>/<product> = caminho do device dentro de device/. Substitua pelos valores reais antes de executar. Onde aparecer <texto> em destaque amarelo, é placeholder.

3. Estrutura final

Tudo que vamos colocar fica concentrado em três lugares dentro do AOSP:

<aosp>/ ├── device/<vendor>/<product>/ │ ├── module/system_ext/memtest_daemon/ ← criar │ │ ├── Android.bp │ │ ├── memtest_daemon.c │ │ ├── memtest_daemon.rc │ │ └── scripts/ │ │ ├── full_memtest.sh │ │ └── ram_diagnostic_deep_verbose_root_exec.sh │ └── sepolicy/system/private/ ← já deve existir │ ├── memtest_daemon.te ← criar │ ├── untrusted_app_memtest.te ← criar │ └── file_contexts ← editar (anexar 2 linhas) └── (algum mk em module/system_ext/app/) └── main.mk ← editar (PRODUCT_PACKAGES_DEBUG)
Caminhos exatos variam por OEM. Em árvores SPRD/Spreadtrum (mpool), SYSTEM_EXT_PRIVATE_SEPOLICY_DIRS já aponta para $(MPOOL)/sepolicy/system/private (declarado em device/sprd/mpool/module/generic/main.mk). Outros OEMs podem ter um caminho diferente — confira com: 
grep -rn "SYSTEM_EXT_PRIVATE_SEPOLICY_DIRS" device/<vendor>/ vendor/<vendor>/ 2>/dev/null

Copiar o daemon nativo e scripts

1.1. Criar o diretório do módulo

mkdir -p <aosp>/device/<vendor>/<product>/module/system_ext/memtest_daemon/scripts

1.2. Copiar os arquivos

SRC=<onde-voce-baixou>/aosp_solution
DST=<aosp>/device/<vendor>/<product>/module/system_ext/memtest_daemon

cp $SRC/native_daemon/memtest_daemon.c                                 $DST/
cp $SRC/native_daemon/memtest_daemon.rc                                $DST/
cp $SRC/native_daemon/Android.bp                                       $DST/
cp $SRC/native_daemon/scripts/full_memtest.sh                          $DST/scripts/
cp $SRC/native_daemon/scripts/ram_diagnostic_deep_verbose_root_exec.sh $DST/scripts/

1.3. O que cada arquivo faz

ArquivoFunçãoOnde vai parar no device
memtest_daemon.c Código fonte do daemon. Compila para um binário ELF nativo. /system_ext/bin/memtest_daemon
memtest_daemon.rc Define o serviço init — usuário root, socket, seclabel, autostart em userdebug. Embutido no init de /system_ext/etc/init/
Android.bp Build script do Soong. Declara cc_binary + 2 prebuilt_etc, todos com system_ext_specific: true. — (só usado durante build)
scripts/full_memtest.sh Teste de fábrica (RAM rápido + storage). WORKDIR em /data/vendor/memtest/. /system_ext/etc/factory/full_memtest.sh
scripts/ram_diagnostic_deep_verbose_root_exec.sh Teste profundo de RAM. /system_ext/etc/factory/ram_diagnostic_deep_verbose_root_exec.sh

Copiar as policies SELinux

2.1. Localizar o diretório system_ext private

grep -rn "SYSTEM_EXT_PRIVATE_SEPOLICY_DIRS" device/ vendor/ 2>/dev/null

Ex. SPRD mpool:

device/sprd/mpool/module/generic/main.mk:2:
SYSTEM_EXT_PRIVATE_SEPOLICY_DIRS := $(MPOOL)/sepolicy/system/private $(SYSTEM_EXT_PRIVATE_SEPOLICY_DIRS)

O diretório é device/sprd/mpool/sepolicy/system/private/.

2.2. Copiar os arquivos .te

SRC=<onde-voce-baixou>/aosp_solution
DST_SEPOL=<aosp>/device/<vendor>/<product>/sepolicy/system/private

cp $SRC/sepolicy/memtest_daemon.te         $DST_SEPOL/
cp $SRC/sepolicy/untrusted_app_memtest.te  $DST_SEPOL/

2.3. O que cada policy faz

ArquivoFunção
memtest_daemon.te Define o domínio SELinux memtest_daemon como coredomain + permissive. Declara o tipo memtest_daemon_exec com atributo system_file_type para passar no neverallow de entrypoint. Mantém só rules essenciais (capabilities, unix_stream_socket).
untrusted_app_memtest.te Permite que o APK (que roda em untrusted_app) escreva e conecte no socket /dev/socket/memtest_daemon.

2.4. Anexar linhas ao file_contexts

Não copia, anexa. O file_contexts existente do device tem regras do OEM — apenas adicionamos no fim.

cat $SRC/sepolicy/file_contexts \
    >> <aosp>/device/<vendor>/<product>/sepolicy/system/private/file_contexts

As 2 linhas que serão acrescentadas:

/system_ext/bin/memtest_daemon          u:object_r:memtest_daemon_exec:s0
/dev/socket/memtest_daemon             u:object_r:memtest_daemon_socket:s0
Por que apenas 2 linhas? Os scripts em /system_ext/etc/factory/ e o workdir em /data/vendor/memtest/ não precisam de label custom — herdam o default da partição. Como o daemon é permissive, ele acessa esses caminhos em runtime sem precisar de allow explícito.

Confirmar wire da sepolicy

Diferente de BOARD_VENDOR_SEPOLICY_DIRS, a maioria das árvores OEM já tem SYSTEM_EXT_PRIVATE_SEPOLICY_DIRS apontando para a pasta onde colocamos os .te. Confira: 

grep -rn "SYSTEM_EXT_PRIVATE_SEPOLICY_DIRS" device/<vendor>/ 2>/dev/null

Se aparecer alguma linha apontando pra pasta onde você copiou os .te → nada a fazer. ✅

Se não aparecer, declare em algum main.mk da partição system_ext:

# Em device/<vendor>/<product>/module/system_ext/main.mk (ou similar)

SYSTEM_EXT_PRIVATE_SEPOLICY_DIRS += device/<vendor>/<product>/sepolicy/system/private
Não use BOARD_VENDOR_SEPOLICY_DIRS para essa policy — vai falhar com erro "unknown type coredomain", porque o compilador vendor não conhece tipos de coredomain.

PRODUCT_PACKAGES — split entre system e system_ext

Como nossos módulos têm system_ext_specific: true, eles devem ser referenciados em um .mk de system_ext. Mas o memtester (utilitário do AOSP) é system. Então split:

4.1. Em algum .mk de system

Tipicamente device/<vendor>/<product>/module/system/app/main.mk ou device.mk: 

PRODUCT_PACKAGES += memtester

4.2. Em algum .mk de system_ext

Tipicamente device/<vendor>/<product>/module/system_ext/app/main.mk: 

# memtest factory tooling (userdebug only)
PRODUCT_PACKAGES_DEBUG += \
    memtest_daemon \
    full_memtest_sh \
    ram_diagnostic_deep_verbose_root_exec_sh
Por que PRODUCT_PACKAGES_DEBUG? Esses módulos só fazem sentido em build userdebug/eng (o init.rc só inicia o daemon se ro.debuggable=1). Usar PRODUCT_PACKAGES_DEBUG garante que não vão pra imagem user de produção.
Não duplique. Se você botar memtest_daemon nos dois .mk, o board check do OEM vai reclamar que módulo system_ext está em .mk de system (ou vice-versa).

Build

5.1. Setup do ambiente

cd <aosp>
source build/envsetup.sh
lunch <seu_target_userdebug>

5.2. Build incremental da sepolicy primeiro

make selinux_policy -j$(nproc)

Erros típicos aqui:

  • "attribute X is not declared" → algum tipo no .te referencia atributo só presente em uma partição. Use só system_file_type (universal).
  • "neverallow violated" → uma allow rule bate em neverallow do AOSP base. Remova a rule e confie em permissive.
  • "module already defined" → você tem cópias duplicadas do Android.bp em dois lugares.

5.3. Build dos módulos

make memtest_daemon -j$(nproc)
make full_memtest_sh ram_diagnostic_deep_verbose_root_exec_sh -j$(nproc)

5.4. Build da imagem completa

make -j$(nproc)

Flashear no device

O daemon e scripts vão pra partição system_ext. Em devices com partições separadas:

adb reboot bootloader
fastboot flash system_ext out/target/product/<product>/system_ext.img
fastboot reboot

Em devices com system_ext mergeado dentro de system:

fastboot flash system out/target/product/<product>/system.img

Ou, mais simples, fazer flash completo:

fastboot flashall
Cuidado com -w: a flag apaga toda a partição /data. Não use a menos que queira limpar os dados do device.

Verificar pós-boot

Com o device ligado e adb conectado:

7.1. Daemon está rodando?

adb shell ps -A | grep memtest_daemon
# memtest_daemon  root  1234  ... /system_ext/bin/memtest_daemon

Se não aparecer:

# Logs do init
adb shell dmesg | grep -i memtest
adb logcat -d | grep -i memtest

# Tentar disparar manualmente
adb shell setprop ctl.start memtest_daemon

7.2. Socket existe?

adb shell ls -laZ /dev/socket/memtest_daemon
# srw-rw-rw- 1 root system u:object_r:memtest_daemon_socket:s0 ...

O Z mostra o label SELinux. Tem que ser memtest_daemon_socket.

7.3. Scripts no lugar?

adb shell ls -laZ /system_ext/etc/factory/
# -rw-r--r-- 1 root root  ... full_memtest.sh
# -rw-r--r-- 1 root root  ... ram_diagnostic_deep_verbose_root_exec.sh

7.4. Binário com label certo?

adb shell ls -laZ /system_ext/bin/memtest_daemon
# -rwxr-xr-x 1 root shell u:object_r:memtest_daemon_exec:s0 ...

7.5. Domínio é permissive?

adb shell ps -AZ | grep memtest_daemon
# u:r:memtest_daemon:s0  root  ...

adb shell cat /sys/fs/selinux/policy 2>/dev/null \
    | grep -ao 'permissive memtest_daemon' \
    || echo "(domínio enforcing — verificar .te tem 'permissive memtest_daemon;')"

7.6. Teste manual via netcat

adb shell
printf 'RUN full_memtest\nEXPECTED_RAM_GB=4\nMIN_WRITE_MBPS=50\nEND\n' \
    | nc -U /dev/socket/memtest_daemon

Esperado: linhas do script saindo, terminando com EXIT:0.

7.7. Verificar AVC denials esperados (não fatais)

adb shell dmesg | grep avc | grep memtest_daemon | tail -20

Como o domínio é permissive, vão aparecer AVC denials (de shell_exec, vendor_data_file, etc.) — eles são apenas registrados, não bloqueiam. Em produção, isso seria limpo via audit2allow; em factory tooling é tolerável.

Instalar e testar o APK

8.1. Onde o APK deve ficar

LocalDomínio resultanteFunciona com nossa policy?
/data/app/ (instalado)untrusted_app✅ Sim
/system/app/untrusted_app✅ Sim
/product/app/untrusted_app✅ Sim
/system/priv-app/priv_app❌ Não — adicionar policy pra priv_app

8.2. APK como módulo do AOSP (recomendado)

No Android.mk ou Android.bp do APK, use:

LOCAL_PRODUCT_MODULE := true
# NÃO use LOCAL_PRIVILEGED_MODULE := true

E adicione em algum .mk de product:

PRODUCT_PACKAGES += RamMemoryTest

8.3. Build incremental do APK

cd MemoryTest/MemoryTest
./gradlew assembleDebug
adb install app/build/outputs/apk/debug/app-debug.apk

Abra o app, cadastre um device, dispare um teste. Se o socket estiver bem configurado, ele conecta e roda. Se der "connection refused", reconfira os passos 7.2 e 7.6.

8.4. Protocolo do daemon (referência)

O APK abre o socket e envia:

RUN full_memtest\n
EXPECTED_RAM_GB=4\n
MIN_WRITE_MBPS=50\n
QUICK_MEMTEST_PERCENT=40\n
...\n
END\n

O daemon:

  1. Valida cada KEY contra a allowlist em ALLOWED_KEYS.
  2. Sanitiza VALUE (rejeita ', ", `, $, \, e bytes não imprimíveis).
  3. Faz setenv() para cada par e exec() o script como root.
  4. Envia stdout/stderr de volta linha a linha.
  5. Termina com EXIT:<code>\n e fecha a conexão.

12. Troubleshooting — erros comuns

Erro de build: 'attribute X is not declared'

Acontece quando o .te referencia um atributo (ex. system_ext_file_type, core_data_file_type) que não está disponível em algum dos contextos de compilação (plat, plat_for_vendor, system_ext). A árvore SPRD recompila o mesmo .te em múltiplos contextos.

Solução: use só system_file_type (declarado em system/sepolicy/public/file.te, universalmente disponível). Mesmo que o binário fique em /system_ext/bin/, o tipo pode ter atributo system_file_type — SELinux usa o label do file_contexts, não o caminho.

Erro de build: neverallow violated

O AOSP base tem várias neverallow em system/sepolicy/public/domain.te que bloqueiam combinações específicas. Comuns:

  • line 716 (Treble socket): app→vendor unix_stream_socket. Solução: daemon como coredomain, não vendor.
  • line 759/783/798 (sock_file/data_file ops): remova as allow rules; permissive cobre em runtime.
  • line 945 (entrypoint): tipo do exec precisa ter system_file_type.
Daemon não inicia no boot

Causa típica: ro.debuggable=0 (build user). O memtest_daemon.rc tem: 

on property:ro.debuggable=1
    start memtest_daemon

Solução: build userdebug ou eng. Em produção, dispare manualmente:

adb shell setprop ctl.start memtest_daemon
"connection refused" do APK ao conectar no socket

Checagem em ordem:

  1. Daemon está rodando? adb shell ps -A | grep memtest
  2. Socket existe? adb shell ls -laZ /dev/socket/memtest_daemon
  3. Socket tem permissão? Deve ser 0666 (definido no .rc).
  4. APK está em domínio untrusted_app? Não pode ser priv_app.
  5. Policy untrusted_app_memtest.te aplicada?
avc: denied mesmo com permissive

Em modo permissive SELinux loga mas não bloqueia. Os denials são informativos. Se uma operação aparenta falhar e tem AVC denial associado, pode ser:

  • O domínio NÃO é permissive (faltou permissive memtest_daemon; no .te) — confirme com ps -AZ.
  • O kernel está em modo enforcing global e algum filtro impede permissive — teste com setenforce 0.
  • A operação falha por outro motivo (DAC, kernel limit), não SELinux.
Script falha por falta de memtester

O memtester precisa estar embarcado na imagem. Em AOSP padrão não vem por default. Adicione ao .mk de system (não system_ext): 

PRODUCT_PACKAGES += memtester

Se não tiver módulo Soong para memtester no seu AOSP, você precisa portar — geralmente cross-compilar e empacotar como prebuilt_binary.

Board check: módulo system_ext em mk de system (ou vice-versa)

Erro tipo: 

Not allowed to configure non-SYSTEM module in SYSTEM partition.
   memtest_daemon -> [SYSTEM_EXT]

Significa que PRODUCT_PACKAGES += memtest_daemon está num .mk de system, mas o Android.bp declara system_ext_specific: true. Mova a referência pra um .mk de system_ext.

Mudei a sepolicy mas avc denied continua

A sepolicy é compilada na imagem. Não basta editar o .te — precisa rebuildar e reflashear: 

make selinux_policy -j$(nproc)
make systemextimage -j$(nproc)
fastboot flash system_ext out/target/product/<product>/system_ext.img

13. Checklist final

  • AOSP buildando para <vendor>/<product> antes de qualquer mudança.
  • Pasta module/system_ext/memtest_daemon/ com Android.bp (com system_ext_specific: true), .c, .rc, scripts.
  • memtest_daemon.te e untrusted_app_memtest.te em sepolicy/system/private/ (ou onde SYSTEM_EXT_PRIVATE_SEPOLICY_DIRS aponta).
  • file_contexts mesclado com as 2 linhas (/system_ext/bin/memtest_daemon e /dev/socket/memtest_daemon).
  • SYSTEM_EXT_PRIVATE_SEPOLICY_DIRS aponta para a pasta dos .te (verificar grep).
  • PRODUCT_PACKAGES += memtester em .mk de system.
  • PRODUCT_PACKAGES_DEBUG += memtest_daemon full_memtest_sh ram_diagnostic_deep_verbose_root_exec_sh em .mk de system_ext.
  • APK referenciado em .mk de product (com LOCAL_PRODUCT_MODULE := true).
  • Build userdebug.
  • Flash da imagem system_ext (ou completa).
  • Verificado: daemon rodando, socket existindo, scripts em /system_ext/etc/factory/, binário em /system_ext/bin/.
  • Domínio memtest_daemon está em permissive (confirmado via ps -AZ).
  • Teste manual via nc -U retornou EXIT:0.
  • APK instalado em untrusted_app (não priv_app) e teste pela UI funcionando.
