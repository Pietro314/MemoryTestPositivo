Integração AOSP — MemoryTest

Guia passo a passo para portar o daemon e scripts ao seu device

Versão do documento: 1.0 Público: engenheiros de plataforma / AOSP Pré-requisito: árvore AOSP buildable do device alvo

1. Arquitetura — por que precisa de daemon?

O APK MemoryTest roda no UID de aplicativo comum (untrusted_app) e não tem acesso ao su. Os scripts de teste, porém, precisam de root para ler life_time de UFS, escrever em /proc/sys/vm/drop_caches, etc.

A solução é um daemon nativo embarcado na partição /vendor/ que inicia como root via init.rc, abre um socket Unix, recebe comandos do APK, e exec os scripts com as variáveis de ambiente do device profile.

APK (UID app, sem root) │ socket Unix /dev/socket/memtest_daemon ▼ memtest_daemon (root, daemon nativo) │ fork + setenv() + exec ▼ /system/bin/sh full_memtest.sh

O APK nunca toca em arquivos de sistema diretamente. Toda ação privilegiada passa pelo daemon, que valida e sanitiza tudo antes de executar.

2. Pré-requisitos

  • Árvore AOSP já clonada e capaz de buildar para o device alvo (ex: ~/aosp/).
  • Build environment funcional: source build/envsetup.sh e lunch <target> sem erro.
  • Permissão de modificar a config do device. Tipicamente em device/<vendor>/<product>/ ou vendor/<vendor>/<product>/.
  • Build do tipo userdebug ou eng — o init.rc autoinicia o daemon condicionado a ro.debuggable=1.
  • Pacote memtester precisa estar disponível na imagem (ver troubleshooting).

2.1. Como descobrir seu <vendor> e <product>

Dentro da árvore AOSP, depois do lunch:

echo $TARGET_DEVICE     # ex: aosp_arm64
echo $TARGET_PRODUCT    # ex: aosp_arm64
ls -d device/*/$TARGET_DEVICE 2>/dev/null
# ex: device/google/aosp_arm64
Convenção neste guia: <aosp> = raiz da árvore AOSP, <vendor>/<product> = caminho do seu device. Substitua pelos valores reais antes de executar qualquer comando. Onde aparecer <texto> em destaque amarelo, é placeholder — substitua.

3. Estrutura final

Tudo que vamos colocar fica concentrado em dois lugares dentro do AOSP:

<aosp>/device/<vendor>/<product>/ ├── memtest_daemon/ ← criar │ ├── Android.bp │ ├── memtest_daemon.c │ ├── memtest_daemon.rc │ └── scripts/ │ ├── full_memtest.sh │ └── ram_diagnostic_deep_verbose_root_exec.sh └── sepolicy/ ← pode já existir └── vendor/ ├── memtest_daemon.te ← criar └── untrusted_app_memtest.te ← criar

E dois arquivos existentes que vamos editar (não criar):

  • <aosp>/device/<vendor>/<product>/sepolicy/vendor/file_contexts — anexar 3 linhas
  • <aosp>/device/<vendor>/<product>/device.mk — anexar 3 entradas em PRODUCT_PACKAGES

Copiar o daemon nativo e scripts

1.1. Criar o diretório

mkdir -p <aosp>/device/<vendor>/<product>/memtest_daemon/scripts

1.2. Copiar os arquivos

SRC=<onde-voce-baixou>/aosp_solution
DST=<aosp>/device/<vendor>/<product>/memtest_daemon

cp $SRC/native_daemon/memtest_daemon.c   $DST/
cp $SRC/native_daemon/memtest_daemon.rc  $DST/
cp $SRC/native_daemon/Android.bp         $DST/
cp $SRC/native_daemon/scripts/full_memtest.sh                       $DST/scripts/
cp $SRC/native_daemon/scripts/ram_diagnostic_deep_verbose_root_exec.sh  $DST/scripts/

1.3. O que cada arquivo faz

ArquivoFunçãoOnde vai parar no device
memtest_daemon.c Código fonte do daemon. Compila para um binário ELF nativo. /vendor/bin/memtest_daemon
memtest_daemon.rc Define o serviço init — usuário root, socket, seclabel, autostart. Embutido no init de /vendor/etc/init/
Android.bp Build script do Soong. Declara cc_binary (daemon) + prebuilt_etc (scripts). — (só usado durante build)
scripts/full_memtest.sh Teste fábrica (RAM rápido + storage). /vendor/etc/factory/full_memtest.sh
scripts/ram_diagnostic_deep_verbose_root_exec.sh Teste profundo de RAM. /vendor/etc/factory/ram_diagnostic_deep_verbose_root_exec.sh
Por que vai para /vendor/ e não /system/? O Android.bp declara vendor: true em todos os módulos — em devices com Treble, vendor é onde fica código específico de hardware. Mantém separação limpa entre AOSP genérico e customização do produto.

Copiar as policies SELinux

2.1. Criar o diretório

mkdir -p <aosp>/device/<vendor>/<product>/sepolicy/vendor

2.2. Copiar os arquivos .te

SRC=<onde-voce-baixou>/aosp_solution
DST_SEPOL=<aosp>/device/<vendor>/<product>/sepolicy/vendor

cp $SRC/sepolicy/memtest_daemon.te         $DST_SEPOL/
cp $SRC/sepolicy/untrusted_app_memtest.te  $DST_SEPOL/

2.3. O que cada policy faz

ArquivoFunção
memtest_daemon.te Define o domínio SELinux memtest_daemon e dá a ele as permissões para ler /sys, /proc/meminfo, escrever em /proc/sys/vm/drop_caches, abrir socket Unix, fork+exec do shell, etc.
untrusted_app_memtest.te Permite que o APK (que roda no domínio untrusted_app) escreva e conecte no socket /dev/socket/memtest_daemon.
Sem essas policies, nada funciona. Mesmo o daemon sendo root, o kernel bloqueia todas as ações via SELinux. Em modo enforcing, a policy é a segunda camada de permissão, independente do UID.

2.4. Mesclar file_contexts

Este passo é diferente: não copia, anexa. O arquivo file_contexts do seu device já existe e tem regras antigas — apenas adicionamos linhas no fim.

Veja se existe:

ls <aosp>/device/<vendor>/<product>/sepolicy/vendor/file_contexts

Se existe → anexe:

cat <onde-voce-baixou>/aosp_solution/sepolicy/file_contexts \
    >> <aosp>/device/<vendor>/<product>/sepolicy/vendor/file_contexts

Se não existe → copie como está:

cp <onde-voce-baixou>/aosp_solution/sepolicy/file_contexts \
   <aosp>/device/<vendor>/<product>/sepolicy/vendor/file_contexts

As 3 linhas que serão acrescentadas:

/vendor/bin/memtest_daemon           u:object_r:memtest_daemon_exec:s0
/vendor/etc/factory(/.*)?            u:object_r:vendor_configs_file:s0
/dev/socket/memtest_daemon           u:object_r:memtest_daemon_socket:s0

Cada linha rotula um caminho com um label SELinux. Sem isso, mesmo com policy permitindo o domínio, o kernel não sabe qual label aplicar ao binário/socket/diretório.

Registrar a sepolicy do vendor

O AOSP precisa saber que esse diretório sepolicy/vendor/ existe e deve ser carregado durante o build.

Opção A — BoardConfig.mk (preferida)

Abra <aosp>/device/<vendor>/<product>/BoardConfig.mk e procure se já tem BOARD_VENDOR_SEPOLICY_DIRS:

# Se já existe, adicione o caminho:
BOARD_VENDOR_SEPOLICY_DIRS += device/<vendor>/<product>/sepolicy/vendor

# Se não existe, crie:
BOARD_VENDOR_SEPOLICY_DIRS := device/<vendor>/<product>/sepolicy/vendor
Variantes em árvores antigas: Use BOARD_PLAT_PRIVATE_SEPOLICY_DIR ou BOARD_SEPOLICY_DIRS em vez de BOARD_VENDOR_SEPOLICY_DIRS em árvores AOSP pre-Treble. No Android 8+ (moderno) é o _VENDOR_.

Opção B — já existe um diretório de sepolicy de vendor

Se o device já tem sepolicy/ carregado em algum BoardConfig.mk, basta colocar nossos .te lá e mesclar o file_contexts. Não precisa adicionar mais nada.

Editar o device.mk

O device.mk é o shopping list — diz ao build quais pacotes devem ir na imagem.

Abra <aosp>/device/<vendor>/<product>/device.mk e procure por uma linha existente como:

PRODUCT_PACKAGES += \
    libc \
    libcutils \
    ...

Adicione no final dessa lista (ou em uma nova linha PRODUCT_PACKAGES +=):

PRODUCT_PACKAGES += \
    memtest_daemon \
    full_memtest_sh \
    ram_diagnostic_deep_verbose_root_exec_sh
Se esquecer este passo, mesmo que o Android.bp defina os módulos, eles não entram na imagem final. O build passa sem erro mas no device não tem nada.

Build

5.1. Setup do ambiente

cd <aosp>
source build/envsetup.sh
lunch <seu_target>      # ex: aosp_arm64-userdebug

5.2. Build incremental (recomendado primeiro)

Compila só nossos módulos para testar se o Android.bp e a sepolicy estão certos:

make memtest_daemon -j$(nproc)
make full_memtest_sh ram_diagnostic_deep_verbose_root_exec_sh -j$(nproc)

Erros típicos aqui:

  • "target not found" → o device.mk não está incluindo. Reconfere passo 4.
  • "sepolicy compile failed" → erro de sintaxe no .te. Mensagem geralmente aponta a linha.

5.3. Build da imagem vendor

make vendorimage -j$(nproc)

Ou imagem completa do device:

make -j$(nproc)

Demora bem mais. Necessário para flashear.

Flashear no device

O caminho típico:

adb reboot bootloader
fastboot flash vendor out/target/product/<product>/vendor.img
fastboot reboot

Se você fez build completo:

fastboot flashall -w     # CUIDADO: -w apaga /data
Cuidado com -w: a flag apaga toda a partição /data. Use só se for flash de imagem nova/limpa. Para apenas atualizar vendor, basta o fastboot flash vendor.

Verificar pós-boot

Com o device ligado e adb conectado:

7.1. Daemon está rodando?

adb shell ps -A | grep memtest_daemon
# memtest_daemon  root   1234  ... /vendor/bin/memtest_daemon

Se não aparecer:

# Ver logs do init
adb shell dmesg | grep -i memtest
adb logcat -d | grep -i memtest

7.2. Socket existe?

adb shell ls -laZ /dev/socket/memtest_daemon
# srw-rw-rw- 1 root system u:object_r:memtest_daemon_socket:s0 ...

O Z mostra o label SELinux. Tem que ser memtest_daemon_socket.

7.3. Scripts no lugar?

adb shell ls -laZ /vendor/etc/factory/
# -rw-r--r-- 1 root root  u:object_r:vendor_configs_file:s0 full_memtest.sh
# -rw-r--r-- 1 root root  u:object_r:vendor_configs_file:s0 ram_diagnostic_deep_verbose_root_exec.sh

7.4. Binário com label certo?

adb shell ls -laZ /vendor/bin/memtest_daemon
# -rwxr-xr-x 1 root shell u:object_r:memtest_daemon_exec:s0 ...

7.5. Teste manual via netcat

adb shell
printf 'RUN full_memtest\nEXPECTED_RAM_GB=4\nMIN_WRITE_MBPS=50\nEND\n' \
    | nc -U /dev/socket/memtest_daemon

Esperado: ver linhas do script saindo, terminando com EXIT:0.

Se travar ou der erro, ver dmesg para denials de SELinux: 
adb shell dmesg | grep -i avc
# avc: denied { read } for ... scontext=u:r:memtest_daemon:s0 ...
Cada linha de denial indica uma permissão que falta no .te. Adicione e re-build.

Instalar e testar o APK

cd MemoryTest/MemoryTest
./gradlew assembleDebug
adb install app/build/outputs/apk/debug/app-debug.apk

Abra o app, cadastre um device, dispare um teste. Se o socket estiver bem configurado, ele conecta e roda. Se der erro de "connection refused", reconfira os passos 7.2 e 7.5.

Protocolo do daemon (referência)

O APK abre o socket e envia:

RUN full_memtest\n
EXPECTED_RAM_GB=4\n
MIN_WRITE_MBPS=50\n
QUICK_MEMTEST_PERCENT=40\n
...\n
END\n

O daemon:

  1. Valida cada KEY contra a allowlist em ALLOWED_KEYS.
  2. Sanitiza VALUE (rejeita ', ", `, $, \, e bytes não imprimíveis).
  3. Faz setenv() para cada par e exec() o script como root.
  4. Envia stdout/stderr de volta linha a linha.
  5. Termina com EXIT:<code>\n e fecha a conexão.

12. Troubleshooting — erros comuns

Daemon não inicia no boot

Causa típica: ro.debuggable=0 (build user). O memtest_daemon.rc tem: 

on property:ro.debuggable=1
    start memtest_daemon

Solução: build userdebug ou eng. Em produção, dispare manualmente:

adb shell setprop ctl.start memtest_daemon
Permission denied no socket pelo APK

Causa: a policy untrusted_app_memtest.te não foi carregada, ou o device tem versão antiga do AOSP que usa untrusted_app_all em vez de untrusted_app. Tente: 

allow untrusted_app_all memtest_daemon_socket:sock_file write;
allow untrusted_app_all memtest_daemon:unix_stream_socket connectto;
avc: denied para alguma operação

Adicione a regra correspondente em memtest_daemon.te e re-build. Em desenvolvimento, você pode rodar em permissive para descobrir tudo de uma vez: 

adb shell setenforce 0    # SELinux permissive
# rode o teste
adb shell dmesg | grep avc | tee denials.log
adb shell setenforce 1    # volta para enforcing

Depois pegue todos os denied do log e gere as regras com audit2allow:

cat denials.log | audit2allow -p out/target/product/<product>/sepolicy

E adicione ao .te.

Script falha por falta de memtester

O memtester precisa estar embarcado na imagem. Em AOSP padrão não vem por default. Adicione ao device.mk: 

PRODUCT_PACKAGES += memtester

Se não tiver módulo Soong para memtester no seu AOSP, você precisa portar — geralmente cross-compilar e empacotar como prebuilt_binary.

Daemon inicia mas socket não aparece

Causa: erro no memtest_daemon.rc ao declarar o socket. Confira a sintaxe da linha: 

socket memtest_daemon stream 0666 root system

Veja também logcat -b all | grep init para erros do init parsing.

"connection refused" do APK ao tentar conectar

Checagem em ordem:

  1. Daemon está rodando? adb shell ps -A | grep memtest
  2. Socket existe? adb shell ls -laZ /dev/socket/memtest_daemon
  3. Socket tem permissão? Deve ser 0666 ou pelo menos w para o grupo do APK.
  4. Policy do APK aplicada? untrusted_app precisa ter connectto e sock_file write.
Mudei a sepolicy mas avc denied continua

A sepolicy é compilada na imagem. Não basta editar o .te — precisa rebuildar e reflashear: 

make selinux_policy -j$(nproc)
make vendorimage -j$(nproc)
fastboot flash vendor out/target/product/<product>/vendor.img

13. Checklist final

  • AOSP buildado para <vendor>/<product> antes de qualquer mudança.
  • Pasta memtest_daemon/ copiada com Android.bp, .c, .rc, scripts.
  • Pasta sepolicy/vendor/ com memtest_daemon.te e untrusted_app_memtest.te.
  • file_contexts mesclado com as 3 linhas.
  • BoardConfig.mk com BOARD_VENDOR_SEPOLICY_DIRS apontando para nossa pasta.
  • device.mk com PRODUCT_PACKAGES += memtest_daemon full_memtest_sh ram_diagnostic_deep_verbose_root_exec_sh.
  • memtester incluído em PRODUCT_PACKAGES.
  • Build userdebug.
  • Flash da imagem vendor.
  • Verificado: daemon rodando, socket existindo, scripts em /vendor/etc/factory/.
  • Teste manual via nc -U retornou EXIT:0.
  • APK instalado e teste pela UI funcionando.
