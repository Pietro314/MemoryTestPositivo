MemoryTest — Guia explicativo

Versão didática para devs que estão chegando agora no projeto. Explica não só o quê, mas por quê. Glossário completo no fim.

Esta página assume que você já programa, mas talvez não tenha experiência específica com Android de fábrica, AOSP, ou Linux a nível de kernel. Cada sigla aparece com explicação na primeira vez. Se esquecer o que algo significa depois, pula pro glossário no fim.

Introdução

O MemoryTest é um aplicativo Android + scripts que testam a memória RAM e o storage interno (chip de armazenamento) de tablets/celulares antes de eles saírem de fábrica pro cliente final.

Por que isso existe? Chips de RAM e storage às vezes vêm com defeito de fábrica. Defeito pequeno passa despercebido no boot — o aparelho liga, conecta na rede, parece normal — mas depois de algumas horas/dias começa a travar, reiniciar sozinho, ou corromper arquivos. Pra cliente final, isso vira RMA (devolução), perda de reputação e custo.

O projeto roda antes do device sair de fábrica, faz uma bateria de testes, e dá um veredicto PASS ou FAIL. Devices que falham voltam pra rework ou descarte.

Contexto: o que é Android, AOSP, kernel

Se você já mexe com Android nativo (apps em Kotlin/Java), pode pular essa seção. Mas se nunca olhou pra dentro do sistema, vale ler.

Android é Linux com camadas em cima

O Android, por dentro, é um sistema operacional baseado no kernel Linux — o mesmo kernel que roda em servidores e Raspberry Pi. Em cima do kernel tem várias camadas (HAL, runtime ART, frameworks Java, apps), mas o coração é Linux.

Isso é importante porque tudo que funciona em Linux funciona no Android: comandos shell (ls, cat, grep), arquivos especiais (/proc, /sys, /dev), permissões Unix (rwxr-xr-x), processos, sinais, etc.

AOSP é o código fonte do Android

AOSP = Android Open Source Project. É o código-fonte completo do Android, mantido pelo Google. Fabricantes (Samsung, Xiaomi, Positivo, etc) baixam o AOSP, customizam pro hardware deles, compilam e flasham no device.

O que a Positivo faz é exatamente isso: pega o AOSP, adiciona drivers do MediaTek (ou Spreadtrum), customiza, compila as imagens (boot.img, system.img, vendor.img, etc) e flasha nos tablets/celulares novos.

Pro MemoryTest funcionar 100%, precisamos alterar o AOSP da Positivo em poucos pontos antes do build. Esses pontos estão documentados mais abaixo em "Mudanças no AOSP".

O kernel expõe o hardware via arquivos virtuais

O Linux tem uma filosofia: "tudo é arquivo". Você não chama uma API pra perguntar "quanto de RAM tem?" — você lê o arquivo /proc/meminfo.

# No PC ou no Android, isso funciona igual:
cat /proc/meminfo

# saída:
# MemTotal:        881540 kB
# MemAvailable:    345880 kB
# ...

Esses arquivos não existem no disco — são gerados pelo kernel em tempo real quando alguém abre. Tem 2 sistemas de arquivos virtuais importantes pro nosso projeto:

  • /proc — info de processos e sistema. Ex: /proc/meminfo, /proc/cpuinfo, /proc/sys/vm/drop_caches.
  • /sys ("sysfs") — info de hardware e drivers. Ex: /sys/class/mmc_host/mmc0/mmc0:0001/cid (o identificador único do chip eMMC).
Por que isso importa pro nosso projeto

Quase toda info que a gente precisa pro teste (RAM total, modelo do chip eMMC, saúde do chip, capacidade) vem de ler arquivos em /sys e /proc. Não usamos APIs Java do Android — leitura direta. Por isso o teste é feito com shell scripts em vez de código Kotlin puro.

O que esse projeto faz, em detalhes

Resumindo, o projeto faz 8 testes no aparelho:

  1. Identifica o device (modelo, fabricante, versão do Android, etc) — pra constar no relatório.
  2. Identifica o chip de storage (vendor, modelo, tipo eMMC ou UFS) — pra rastreabilidade.
  3. Lê a saúde do storage (quanto já foi "gasto" da vida útil) — pra rejeitar chips que vieram desgastados.
  4. Mede a capacidade do storage (4 GB? 8 GB? 64 GB?) — pra confirmar que tem o tamanho que devia.
  5. Lê info de RAM (total e disponível) — pra confirmar que tem a RAM esperada.
  6. Roda um teste de leitura/escrita no storage com 512 MB de dados aleatórios e confere se o que escreveu volta igual (hash MD5) — pega chips que corrompem dados.
  7. Roda o memtester na RAM com 16 padrões diferentes — pega chips de RAM com células defeituosas.
  8. Lê o log do kernel (dmesg) procurando mensagens de erro de hardware — pega problemas que o kernel já detectou.

Cada teste produz um veredicto. Se algum falha, o teste geral vira FAIL com a razão listada.

Os 2 caminhos para rodar o teste

O mesmo conjunto de testes pode ser executado de duas formas diferentes. A diferença é quem chama os scripts.

Caminho A — APK platform-signed (a "solução de produção")

Tem um aplicativo Android (APK) que vem pré-instalado no firmware do device. Ele tem uma tela bonita pro operador da fábrica, lista de testes disponíveis, histórico no banco de dados, etc.

Quando o operador clica em "Rodar teste", o APK extrai o script shell que vem dentro dele (em assets/) e roda esse script via ProcessBuilder (uma API Java pra spawn de processo).

Vantagens: UI no próprio device, integra com banco de perfis, fluxo profissional.

Requisito: precisa de mudanças no AOSP da fábrica (descritas abaixo).

Caminho B — ScriptOnly via ADB (a "solução de bancada")

Não tem APK. O QA conecta o device no PC via USB e roda os scripts direto do PC via adb shell. Os scripts são empurrados pro device, executam lá, geram um log, e o log é puxado de volta pro PC.

Vantagens: não precisa modificar nada no AOSP. Funciona em qualquer device com USB debug ativo.

Desvantagem: precisa cabo + PC. Não serve pra linha de produção em massa.

O que é ADB

ADB = Android Debug Bridge. É uma ferramenta da Google que permite o PC mandar comandos pra um device Android via USB (ou WiFi). Comandos típicos: adb install <apk>, adb shell ls /, adb push arquivo /sdcard/. Vem com o Android SDK.

Os scripts são os mesmos

Tanto o caminho A quanto o B usam o mesmo arquivo full_memtest.sh — ele fica em dois lugares (dentro do APK e dentro do zip ScriptOnly), mas o conteúdo é idêntico. Toda a lógica de teste tá no shell script. APK e ADB são só formas diferentes de invocar ele.

Mas os 2 caminhos NÃO são 100% equivalentes

O script é igual, mas quem roda ele tem privilégios diferentes. Em resumo:

  • APK platform_app roda como UID system (1000), num contexto privilegiado. Ganha mlock unlimited garantido (crítico pro memtester), tem acesso a vários grupos Unix (incluindo disk), pode mexer em /data/system, e mostra UI no device.
  • ScriptOnly roda como UID shell (2000), via adb. mlock depende da config do device (pode ser baixo em build user), não tem grupo disk, e precisa de PC plugado. Em compensação, escala pra root facilmente com adb root em userdebug e não depende de modificações no AOSP.

No nosso caso (L400/SPRD em userdebug com SELinux Permissive), os 2 caminhos conseguem fazer praticamente os mesmos testes porque os arquivos críticos (/sys/class/mmc_host/..., /proc/meminfo) são world-readable (modo 0444) — qualquer UID lê. Mas em produção (build user + SELinux Enforcing), o APK platform_app é mais robusto e cobre coisas que o ScriptOnly não cobriria.

Regra prática: APK = caminho de produção. ScriptOnly = caminho de bancada/debug.

Mudanças no AOSP (pra caminho A funcionar)

Pra o APK MemoryTest funcionar com cobertura completa, a árvore AOSP da Positivo precisa ter 4 mudanças:

Mudança 1 — Empacotar o binário memtester

O memtester é uma ferramenta C open-source que testa RAM com 16 padrões. Ele não vem com o Android stock. Precisa ser compilado pra ABI do device (arm32, arm64, etc) e empacotado no firmware em /system/bin/memtester.

# No device.mk ou main.mk da árvore AOSP:
PRODUCT_PACKAGES += memtester

O source do memtester fica em external/memtester/ com um Android.bp declarando como compilar.

Mudança 2 — Empacotar o APK MemoryTest como prebuilt

O APK que a gente compila (com ./gradlew assembleRelease) precisa ser incluído no firmware como um app pré-instalado privilegiado. Isso é feito declarando-o em Android.bp ou Android.mk:

// packages/apps/MemoryTest/Android.bp
android_app_import {
    name: "MemoryTest",
    apk: "MemoryTest.apk",
    certificate: "platform",
    privileged: true,
}

E adicionar no device.mk:

PRODUCT_PACKAGES += MemoryTest

O ponto crucial é o certificate: "platform". Quando você instala um APK normalmente (adb install), ele é assinado pelo seu certificado de desenvolvedor e roda como um app comum (UID alto, restrito). Mas quando o AOSP empacota com certificate: "platform", ele re-assina o APK com a chave de plataforma do device. Isso transforma o app em platform_app, que tem permissões muito maiores.

Mudança 3 — Configurar SELinux como Permissive

O SELinux é um sistema de segurança do Linux que bloqueia acessos mesmo quando as permissões Unix permitem. Ele tem 2 modos: Enforcing (bloqueia o que não está permitido) e Permissive (só loga, não bloqueia).

Em produção pra cliente final, Android sempre vem com SELinux Enforcing. Mas pra teste de fábrica, deixamos Permissive — assim o teste consegue ler todos os arquivos de /sys que precisa, sem ter que escrever policy customizada pra cada caso.

Como configurar depende do SoC:

  • SPRD (Spreadtrum/Unisoc) — adicionar no BoardConfig.mk: 
    BOARD_KERNEL_CMDLINE += androidboot.selinux=permissive
  • MediaTek MT6761 (e similares) — o BOARD_KERNEL_CMDLINE é ignorado nesses SoC (a cmdline real é montada pelo bootloader LK em runtime). Precisa editar o project file do LK: 
    # vendor/mediatek/proprietary/bootable/bootloader/lk/project/k61v1_32_bsp_1g.mk
PRJ_SELINUX_STATUS := 2     # 2 = Permissive
    E rebuildar/flashar o lk.img.

Mudança 4 — Build incremental e flash

Depois das 3 mudanças acima:

cd <AOSP_ROOT>
source build/envsetup.sh
lunch <produto>
m productimage     # ou systemimage, conforme onde está o APK
# Flash:
fastboot flash product out/target/product/<device>/product.img

Build incremental (depois que out/ está populado) é rápido: 1-3 min só pra re-empacotar.

SELinux: o "portão" que controla acesso a tudo

Essa parte é importante porque quase todo problema "estranho" no projeto envolve SELinux. Vale entender.

Imagine que cada arquivo do sistema tem 2 portões pra atravessar:

  1. DAC (Discretionary Access Control) — o sistema Unix tradicional. É aquele -rw-r--r-- que você vê com ls -l. Permite/nega baseado em quem é o dono (usuário e grupo) do arquivo e do processo.
  2. SELinux MAC (Mandatory Access Control) — uma camada extra de segurança. Permite/nega baseado em contextos de segurança. Cada processo tem um contexto (ex: u:r:platform_app:s0) e cada arquivo também (ex: u:object_r:sysfs:s0). Há regras explícitas dizendo "processo do tipo X pode ler arquivo do tipo Y".

Os 2 portões precisam ser passados. Se o DAC nega, SELinux nem é consultado. Se o DAC permite mas SELinux nega (em modo Enforcing), o acesso falha.

Quando colocamos SELinux Permissive, o segundo portão fica sempre aberto — só DAC vale. Como a maioria dos arquivos de /sys que nos interessam tem DAC 0444 (todo mundo lê), conseguimos ler quase tudo sem precisar escrever policies customizadas.

Por que não rodamos Enforcing

Em teoria, dava pra escrever uma policy SELinux customizada (arquivos .te) liberando exatamente os acessos que precisamos, e manter Enforcing. O problema é: cada device tem driver diferente, cada driver expõe sysfs em path diferente, e cada policy custa horas/dias pra escrever e testar. Pra contexto de fábrica, Permissive é prático e seguro o suficiente — o aparelho não tá conectado à internet rodando apps maliciosos.

Por que precisa de "mlock unlimited"

Esse é o ponto mais sutil do projeto. Quando o memtester aloca, digamos, 200 MB de RAM pra testar, ele precisa garantir que o kernel não vai mover essa memória pra swap nem reciclar as páginas. Se o kernel realocar enquanto o teste rola, o teste é inválido — você não tá testando a mesma RAM o tempo todo.

Pra evitar isso, o memtester chama mlock() — uma syscall do Linux que diz "essa região de RAM é minha, não mexe". Mas mlock tem um limite por processo, chamado RLIMIT_MEMLOCK. Esse limite é definido pelo sistema baseado em quem é o processo:

Contexto do processoRLIMIT_MEMLOCK típico
untrusted_app (app comum do Play Store)~8 MB
shell (UID 2000, usado pelo adb)~64 MB
platform_app (priv-app assinado com platform key)unlimited
root (UID 0)unlimited
O perigo do "fake-fast PASS"

Se o memtester roda como untrusted_app, ele tenta alocar 200 MB e travar com mlock. O mlock falha (limite ~8 MB). O memtester então reduz automaticamente o tamanho do teste pra ~8 MB, roda os 16 padrões em 8 MB (rapidíssimo, ~5 segundos), e retorna PASS — mas testou só 4% da RAM. O operador vê PASS e libera o aparelho com RAM defeituosa pra cliente.

Por isso o APK obrigatoriamente precisa ser platform_app. Sem isso, o teste é cosmético.

Teste 1 — Identificação do device

O que faz: coleta info do device pra constar no relatório. Não tem PASS/FAIL — é só meta-info.

Como funciona

Usa o comando getprop, que lê system properties do Android. Essas properties são pares chave=valor preenchidos pelo bootloader/init/build system. Ex: ro.product.model contém o nome do modelo (ex: "L400").

Comandos lidos

getprop ro.serialno              # número de série único
getprop ro.product.model         # modelo (L400, T2070D, TL10)
getprop ro.product.brand         # marca (positivo)
getprop ro.product.device        # codinome interno do device
getprop ro.product.board         # codinome do board (k61v1_32_bsp_1g)
getprop ro.product.cpu.abi       # ABI (armeabi-v7a, arm64-v8a)
getprop ro.hardware              # SoC (mt6761, sp9863a)
getprop ro.soc.manufacturer      # fabricante do SoC (MediaTek, Spreadtrum)
getprop ro.build.version.release # versão do Android (11, 12)
getprop ro.build.fingerprint     # string única do build
getprop ro.build.type            # user, userdebug, eng
getprop ro.debuggable            # 0 ou 1

Permissões

Nenhuma especial. getprop é acessível por qualquer UID, qualquer contexto SELinux. Mesmo um app untrusted_app consegue.

O que é "ABI"

ABI = Application Binary Interface. É o "formato binário" da arquitetura do processador. Códigos compilados pra armeabi-v7a (ARM 32-bit) não rodam em devices arm64-v8a (ARM 64-bit), e vice-versa. Por isso temos 2 versões do memtester: memtester-arm32 e memtester-arm64.

O que são "user, userdebug, eng"

São tipos de build do AOSP:

  • user — build de produção. Sem root, sem su, sem ferramentas de debug. É o que vai pro cliente final.
  • userdebug — igual ao user mas com su disponível, root habilitado em adb root, mais logs. É o que QA usa pra testar.
  • eng — engineering. Tudo aberto, máximo de logs, ferramentas extras. Usado por engenheiros AOSP.

Pra fábrica usamos userdebug nos protótipos e mudamos pra user antes de mass production.

Teste 2 — Identificação do storage (vendor/modelo)

O que faz: descobre o fabricante e modelo do chip de armazenamento (eMMC ou UFS). Importante pra rastrear lotes — se vários devices falharem com o mesmo modelo de chip, é problema do fornecedor.

O que é eMMC e UFS

São dois padrões de chips de armazenamento flash usados em celulares.

  • eMMC (embedded MultiMediaCard) — padrão mais antigo, usado em devices entry-level. Mais lento (~50-100 MB/s write). Comum em tablets baratos como L400.
  • UFS (Universal Flash Storage) — padrão mais novo, usado em celulares high-end. Muito mais rápido (~500-1000 MB/s). Usa interface serial (SCSI).

Os dois guardam dados de forma persistente, mas a forma de conversar com eles é diferente — por isso o código precisa tratar os dois casos.

Como descobre — UFS primeiro

# Procura o "health descriptor" — diretório especial que o driver UFS cria
/sys/devices/platform/soc/*ufs*/health_descriptor
/sys/bus/platform/devices/*ufs*/health_descriptor

# Se achar, dentro dele tem o nome do vendor e produto:
<dir>/string_descriptors/manufacturer_name    # ex: "SAMSUNG"
<dir>/string_descriptors/product_name         # ex: "KLM8G1GETF-B041"

Como descobre — eMMC (se UFS não existir)

# Procura o "CID" — Card IDentification, 16 bytes únicos do chip
/sys/class/mmc_host/mmc*/mmc*:*/cid

# Junto tem o vendor e modelo legíveis:
/sys/class/mmc_host/mmc*/mmc*:*/name      # PNM em ASCII (ex: "FN62BB")
/sys/class/mmc_host/mmc*/mmc*:*/manfid    # MID (ex: 0x000015 = Samsung)
Como decodificar o CID manualmente

O CID é uma string hexadecimal de 32 caracteres (16 bytes). Os bytes têm significados específicos:

  • Byte 1-2 → MID (Manufacturer ID)
  • Byte 5-14 → PNM (Product Name) em hex — decode pra ASCII pra obter o nome

Ex: CID 150100464e3632424209f6450647b9bf

  • MID = 15 → Samsung
  • PNM hex = 00464e3632 → decode = "FN62" (modelo Samsung KLMxFN62 family)

Vendors comuns de eMMC

MIDVendor
0x15Samsung
0x90SK Hynix
0x70Kingston
0x11Toshiba/Kioxia
0x13Micron

Permissões

Os arquivos em /sys/class/mmc_host/... são tipicamente 0444 (world-readable). Qualquer UID lê, em qualquer contexto SELinux Permissive.

Teste 3 — Saúde do storage (LifeTime + Pre-EOL)

O que faz: lê 2 valores que o próprio chip eMMC/UFS calcula internamente sobre quanto da vida útil já foi usada. Importante porque um chip muito desgastado já vai sair com pouco tempo de vida — não vale entregar pra cliente.

O que é LifeTime e Pre-EOL

Chips eMMC/UFS são feitos de células de memória flash. Cada célula aguenta um número limitado de escritas (~10.000 a 100.000) antes de "queimar". O controlador do chip conta as escritas e mantém 2 estimativas internas:

  • LifeTime A — desgaste das células do tipo A (geralmente SLC, mais resistente — usado pra metadados).
  • LifeTime B — desgaste das células do tipo B (geralmente MLC/TLC, menos resistente — usado pra dados).
  • Pre-EOL (Pre End-of-Life) — sinal binário de "tá perto do fim?". Vai de Normal → Warning → Critical conforme o controlador esgota os "spare blocks" (blocos de reserva pra reposição).

Interpretação dos valores

Valor (hex)LifeTime A/B (% usado)Pre-EOL
0x00não definido (chip antigo)—
0x010–10% usado (basicamente novo)Normal
0x0210–20% usadoWarning (~80% spare consumidos)
0x0320–30% usadoCrítico (spare esgotado — FAIL)
...(+10% por nível)—
0x0A90–100% usado—
0x0Bpassou de 100% (vida excedida)—

Onde está o valor

Existem 3 formatos diferentes que vendors usam pra expor isso. O script tenta na ordem:

  1. Arquivos separados (Samsung, Qualcomm, etc): 
    /sys/class/mmc_host/mmc0/mmc0:0001/life_time_type_a
/sys/class/mmc_host/mmc0/mmc0:0001/life_time_type_b
/sys/class/mmc_host/mmc0/mmc0:0001/pre_eol_info
  2. Arquivo único (Allwinner, MediaTek MT6761): 
    /sys/class/mmc_host/mmc0/mmc0:0001/life_time
# conteúdo: "0x01 0x01"  (A e B separados por espaço)
  3. Caminho MTK alternativo (alguns kernels MediaTek antigos): 
    /proc/bootdevice/life_time_est_typ_a
/proc/bootdevice/life_time_est_typ_b
/proc/bootdevice/pre_eol_info

Limitação importante

O kernel pode não expor

Os valores SEMPRE existem no chip (bytes 267-269 do EXT_CSD da especificação JEDEC eMMC). Mas o driver MMC do kernel é quem escolhe criar os arquivos em /sys. Alguns kernels (especialmente MTK stock antigos) não criam — aí ficamos sem essa info.

Alternativas, todas pesadas:

  • Empacotar a ferramenta mmc-utils e rodar mmc extcsd read /dev/block/mmcblk0 — precisa root real (CAP_SYS_RAWIO) por causa de um ioctl protegido.
  • Patchar o driver MMC do kernel pra criar os arquivos — trabalho de BSP, semanas.
  • Aceitar "N/A" no relatório e usar só Pre-EOL como termômetro.

Teste 4 — Capacidade do storage

O que faz: mede o tamanho real do chip de storage e compara com o tamanho esperado do profile. Se um device é especificado pra ter 64 GB e a gente medir 32 GB, alguém errou no almoxarifado.

Método primário

# Primeiro descobre qual é o block device do userdata:
STOR_BLOCK=$(readlink -f /dev/block/by-name/userdata | sed 's/p[0-9]*$//')
# Resultado típico: /dev/block/mmcblk0

# Pergunta o tamanho total:
blockdev --getsize64 /dev/block/mmcblk0
# Retorna bytes do device inteiro (todas as partições somadas)

Fallback se blockdev falhar

# Se blockdev der erro (DAC restritivo, etc), usa df:
df /data | awk 'NR==2{print $2}'    # KB do /data
# Subestima, mas serve pra confirmar a ordem de grandeza
O que é block device, by-name, userdata

Block device é como o Linux representa dispositivos de armazenamento — arquivos especiais em /dev/block/. /dev/block/mmcblk0 = o chip eMMC inteiro. /dev/block/mmcblk0p12 = partição 12 desse chip.

by-name/ é um diretório onde o Android cria links simbólicos com nomes amigáveis pras partições. /dev/block/by-name/userdata aponta pra partição onde fica /data. readlink -f resolve o link pra encontrar o block device real.

Teste 5 — Informações de RAM

O que faz: lê quanto de RAM o device tem, quanto tá disponível, e tenta identificar o tipo de LPDDR. Compara o total com o esperado do profile (PASS se >= esperado).

Comandos

grep MemTotal     /proc/meminfo | awk '{print $2}'   # KB total instalado
grep MemAvailable /proc/meminfo | awk '{print $2}'   # KB livre pra alocar AGORA
Diferença entre MemTotal e MemAvailable

MemTotal é a RAM física instalada no aparelho (depois do kernel reservar uma parte pra si). Num device com 1 GB físico, MemTotal vem como ~860 MB (kernel consumiu 164 MB pra coisas internas).

MemAvailable é quanto a gente pode pedir pro kernel agora. É bem menor — o Android já ocupou várias centenas de MB com zygote, system_server, surfaceflinger, etc. Num device com 1 GB total, MemAvailable fica em ~300-400 MB.

Pro teste de RAM, usamos MemAvailable como base — não dá pra testar o que o sistema tá usando, senão dá OOM.

LPDDR type

getprop ro.boot.ddr_type
getprop ro.boot.dram_type
getprop vendor.boot.ddr_type
cat /proc/bootdevice/dram_type    # fallback MTK
O que é LPDDR

LPDDR = Low Power Double Data Rate. É o tipo de RAM usada em celulares (versão de baixo consumo da DDR usada em PCs). Tem várias gerações:

  • LPDDR3 — gerações antigas, devices entry-level (até ~2016).
  • LPDDR4 / LPDDR4X — mainstream (2016-2020).
  • LPDDR5 / LPDDR5X — flagships atuais.

Saber o tipo é informativo, mas não muda muito o teste. Em muitos devices essa property vem vazia — não é defeito, é o bootloader que não populou.

Teste 6 — I/O Test do storage (dd)

O que faz: escreve 512 MB de dados aleatórios no storage, lê de volta, mede velocidades de write e read, e confere a integridade comparando hash MD5 antes e depois. É o teste real do storage — pega chips que corrompem dados ou tão muito lentos.

Sequência completa

# Vai pro workdir
cd /data/data/<package>/files/memtest_work    # ou /data/local/tmp/memtest_work no ScriptOnly

# === Write ===
T1=$(date +%s%3N)                            # timestamp em ms
dd if=/dev/urandom of=testfile bs=4M count=128 conv=fsync
# Explicação do dd:
#   if=/dev/urandom  : input file = gerador de bytes aleatórios do kernel
#   of=testfile      : output file = nome do arquivo a ser criado
#   bs=4M            : block size 4 MB (cada read/write copia 4 MB)
#   count=128        : faz isso 128 vezes (total = 4M * 128 = 512 MB)
#   conv=fsync       : forçar flush pro disco no final, sem ficar cacheado em RAM
T2=$(date +%s%3N)
WRITE_MS=$((T2-T1))
WRITE_MBPS=$(( 512 * 1000 / WRITE_MS ))      # MB/s

# === Hash antes ===
md5sum testfile > hash_before.txt

# === Limpar cache (se for root) ===
sync                                          # garante que tudo foi escrito
echo 3 > /proc/sys/vm/drop_caches             # PRECISA UID 0 — limpa page cache
# Se não for root, falha silenciosamente (não bloqueia)

# === Read ===
T3=$(date +%s%3N)
dd if=testfile of=/dev/null bs=4M             # lê e descarta
T4=$(date +%s%3N)
READ_MS=$((T4-T3))
READ_MBPS=$(( 512 * 1000 / READ_MS ))

# === Hash depois ===
md5sum testfile > hash_after.txt
diff hash_before.txt hash_after.txt           # tem que ser igual
O que é /dev/urandom

É um arquivo especial do Linux que gera bytes aleatórios "infinitamente" quando você lê dele. Usado em testes porque dados aleatórios são incompressíveis — o controlador do storage não pode "trapacear" comprimindo, então a velocidade medida é real.

O que é page cache e por que drop_caches importa

Quando você lê um arquivo no Linux, o kernel guarda uma cópia na RAM (page cache). Se você ler de novo logo em seguida, ele entrega da RAM em vez de ir no disco — muito mais rápido.

Pro nosso teste, isso é problema: se a gente escreve e logo lê, a leitura pode vir do cache RAM em vez do storage de verdade, e mediríamos velocidade de RAM (super alta) achando que é storage.

Por isso echo 3 > /proc/sys/vm/drop_caches entre write e read — força o kernel a esquecer o cache. Como exige root, sem root o read pode vir inflado. Mitigamos usando 512 MB de teste (geralmente maior que o cache disponível).

Critérios de FAIL

  • WRITE_MBPS abaixo de MIN_WRITE_MBPS (do profile)
  • READ_MBPS abaixo de MIN_READ_MBPS (do profile)
  • Hash MD5 antes ≠ hash MD5 depois (corrupção de dados)
  • dd retornou exit code ≠ 0 (erro de I/O)

Teste 7 — Teste de RAM (memtester)

O que faz: exercita células de RAM com 16 padrões diferentes pra detectar defeitos físicos. É o teste mais crítico — falha aqui significa chip ruim.

O que é o memtester

É uma ferramenta open-source em C escrita por Charles Cazabon. Aloca um pedaço grande de RAM, escreve padrões específicos, lê de volta e checa se bate. Cada padrão exercita um tipo de defeito:

  • Stuck Address — descobre células que sempre retornam o mesmo valor independente do que você escreveu.
  • Walking Ones / Zeroes — escreve um bit ligado e os outros desligados, anda esse bit por todas posições — descobre células acopladas (uma afeta a outra).
  • Checkerboard — alterna bits 010101... ou 101010... pra detectar problemas de pareamento.
  • Bit Flip — inverte bits e testa retenção.
  • Random Value — escreve aleatório, lê, compara — pega defeitos pattern-sensitive.
  • Compare XOR/SUB/MUL/DIV/OR/AND — operações aritméticas/lógicas pra ativar paths diferentes no decoder.
  • ... e mais 5 padrões.

Como o script roda

# Localiza o binário (testa os caminhos em ordem):
for candidate in /system/bin/memtester /system/xbin/memtester \
                 /vendor/bin/memtester /data/local/tmp/memtester; do
    [ -x "$candidate" ] && MEMTESTER_BIN="$candidate" && break
done

# Calcula tamanho do teste (50% do MemAvailable, capped em 512 MB):
MEMTEST_MB=$(( MEM_AVAIL_MB * 50 / 100 ))
[ "$MEMTEST_MB" -gt 512 ] && MEMTEST_MB=512

# Executa em background pra poder fazer polling:
memtester ${MEMTEST_MB}M 1 > memtester.log 2>&1 &
MEMTESTER_PID=$!

# Loop de polling — reporta progresso a cada 10s, mata se passar timeout:
while kill -0 "$MEMTESTER_PID" 2>/dev/null; do
    sleep 10
    log "memtester em execução... ${ELAPSED}s/${TIMEOUT}s"
    if [ "$ELAPSED" -ge "$TIMEOUT" ]; then
        kill -9 "$MEMTESTER_PID"
        fail "memtester excedeu timeout"
    fi
done

O critério de FAIL é triplo

  • Exit code ≠ 0 (memtester detectou erro)
  • Saída contém "FAILURE" (algum padrão falhou)
  • Timeout (10 min no quick, 1h no deep)

Cobertura realista

Em um device com 1 GB de RAM:

  • ~860 MB visíveis pro kernel (MemTotal)
  • ~340 MB disponíveis depois do Android subir (MemAvailable)
  • ~170 MB testados pelo memtester (50% do available)

Ou seja, ~20% das células físicas são tocadas em um run. Parece pouco, mas como o kernel aleatoriza qual página fica onde, ao longo de várias execuções diferentes (em devices diferentes do lote) quase todas células são exercitadas estatisticamente.

Pra cobertura próxima de 100% precisaria teste offline (memtest86+ no bootloader, com Android desligado) — projeto totalmente diferente.

Teste 8 — Análise do dmesg

O que faz: lê o log do kernel e procura mensagens de erro de hardware. Se o kernel já detectou algo errado durante o boot ou durante o teste, isso aparece no dmesg.

O que é dmesg

dmesg = diagnostic message. É um buffer circular do kernel onde ele escreve mensagens de log: dispositivos detectados, erros de drivers, eventos de power management, panic, etc. dmesg sem argumentos imprime tudo. Em Android é a primeira coisa que olhamos quando algo está estranho.

Padrões procurados (factory test)

grep -iE "I/O error|ufs error|mmc error|memory corruption|hardware error|ecc error|bad block|uncorrectable|panic"

O que cada termo indica

TermoSignifica
I/O errorFalha de leitura/escrita no storage
mmc error / ufs errorDriver MMC/UFS reportou erro
memory corruptionKernel detectou que RAM tá corrompendo dados
ecc errorErro corrigido por ECC — sinal precoce de degradação
bad blockBloco do storage marcado como ruim
uncorrectableErro de ECC que NÃO foi corrigível — perda real
panicKernel parou — situação crítica

Permissão

Em Android 10+, dmesg pode estar restrito (precisa root). Se vier vazio, o script reporta "dmesg: não disponível" mas não falha o teste — análise dmesg é complementar.

Deep RAM — o teste pesado

Existe um segundo script, ram_diagnostic_deep_verbose_root_exec.sh, que faz só teste de RAM mas muito mais profundo. Usado pra:

  • Devices que voltaram com reclamação de cliente (suspeito de RAM defeituosa)
  • Homologação de novo lote de chips
  • Confirmação de defeito antes de abrir RMA com fornecedor

O que muda

AspectoFactory (quick)Deep

Por que mais loops

Cada loop testa AS MESMAS células alocadas. Defeitos intermitentes (timing, retenção, térmicos) podem só aparecer na 2ª ou 3ª passagem, quando o chip já tá aquecido. 1 loop pega ~75% dos defeitos; 3 loops pega ~90%.

Dump completo do /proc/meminfo

O deep faz cat /proc/meminfo inteiro pro log, em vez de só pegar MemTotal/MemAvailable. Útil pra correlacionar depois — se o teste falhou, dá pra ver se tinha SwapIn alto, fragmentação, etc.

Padrões dmesg do deep

grep -iE "memory corruption|hardware error|ecc error|uncorrectable|panic|oom|out of memory|page allocation failure|bad page|kernel BUG"

Termos extras vs factory:

  • oom / out of memory — OOM killer disparou (sistema ficou sem RAM)
  • page allocation failure — kernel não conseguiu alocar memória (fragmentação ou pressão extrema)
  • bad page — kernel detectou página com corruption
  • kernel BUG — assertion failure no kernel (frequentemente disparado por RAM defeituosa)

Como replicar em outro projeto

Se você precisa fazer testes parecidos no projeto que cuida, tem 2 caminhos:

Caminho minimalista (só scripts)

  1. Copie full_memtest.sh e ram_diagnostic_deep_verbose_root_exec.sh do nosso repositório.
  2. Compile memtester pra ABI do seu device. Source: pyropus.ca/software/memtester ou através do AOSP em external/memtester/.
  3. Crie um wrapper que faça adb push dos scripts + binário pro device, rode via adb shell, e puxe o log de volta.
  4. Crie um arquivo .conf com os thresholds do seu SKU (MIN_WRITE_MBPS, EXPECTED_RAM_GB, etc).

Caminho APK (com UI no device)

  1. Copie a classe ScriptRunner.kt do nosso projeto — ela extrai um asset, roda via ProcessBuilder e emite eventos linha-a-linha.
  2. Embarque os scripts em assets/ do seu APK.
  3. Compile o APK normal (./gradlew assembleRelease).
  4. Empacote o APK como prebuilt no AOSP do device (ver Mudanças no AOSP).
  5. Adicione PRODUCT_PACKAGES += SeuTeste memtester e configure SELinux Permissive.
  6. Rebuild + flash. O AOSP re-assina automaticamente.

Validar a integração

Use o pre_check.sh do nosso ScriptOnly — ele lista o que funciona e o que está bloqueado num device específico, sem alterar nada. Comando: bash pre_check.sh.

📖 Glossário completo

Todas as siglas e termos técnicos usados na página, em ordem alfabética.

ABI (Application Binary Interface)
Formato binário compatível com uma arquitetura específica de processador. Códigos compilados pra armeabi-v7a só rodam em ARM 32-bit; arm64-v8a só em ARM 64-bit. É por isso que temos 2 binários do memtester (arm32 e arm64).
adb (Android Debug Bridge)
Ferramenta de linha de comando da Google que permite o PC interagir com um device Android via USB/WiFi. Vem com Android SDK. Comandos típicos: adb install, adb shell, adb push, adb logcat.
adb root
Comando que reinicia o daemon adb no device rodando como UID 0 (root). Só funciona em builds userdebug/eng. Em devices MTK no Windows às vezes quebra o adb-server — preferir adb shell su 0.
Android.bp / Android.mk
Arquivos que definem como o AOSP compila um módulo. Android.bp é o formato moderno (Soong, sintaxe JSON-like). Android.mk é o antigo (Make). Servem pra mesma coisa: declarar o que é o módulo (app, lib, binário) e suas dependências.
AOSP (Android Open Source Project)
Código-fonte completo do Android, mantido pelo Google. Cada fabricante baixa, customiza pro hardware deles, compila e flasha no device.
BoardConfig.mk
Arquivo da árvore AOSP que define configurações específicas do hardware: ABI, kernel cmdline, partições, etc. Fica em device/<vendor>/<device>/BoardConfig.mk.
block device
Arquivo especial em /dev/block/ que representa um dispositivo de armazenamento. Ex: /dev/block/mmcblk0 = o chip eMMC inteiro. /dev/block/mmcblk0p12 = partição 12.
BOARD_KERNEL_CMDLINE
Variável do BoardConfig.mk que define argumentos passados pro kernel no boot. Ex: androidboot.selinux=permissive. Em SoCs MediaTek (MT6761), essa variável é ignorada — a cmdline é montada pelo LK em runtime.
CID (Card Identification)
Identificador único de 16 bytes de um chip eMMC, gravado de fábrica no controlador. Inclui MID (Manufacturer ID) e PNM (Product Name). Exposto em /sys/class/mmc_host/mmc0/mmc0:0001/cid.
cmdline (kernel command line)
String de argumentos passada pro kernel Linux no boot. Inclui parâmetros como androidboot.selinux=permissive, console=tty0, etc. Montada pelo bootloader.
DAC (Discretionary Access Control)
Sistema de permissões Unix tradicional, baseado em dono (user/group) e modo (rwxrwxrwx). É o que você vê com ls -l. Funciona em conjunto com SELinux MAC.
dd
Comando Unix antigo (anos 70) pra cópia byte-a-byte entre arquivos. Sintaxe: dd if=<input> of=<output> bs=<block_size> count=<n>. Usado no nosso projeto pra testar velocidade de I/O do storage.
dmesg (diagnostic message)
Buffer circular do kernel Linux com mensagens de log: drivers, erros, eventos. dmesg (sem args) imprime tudo. Restrito em Android 10+ — pode precisar root.
drop_caches
Arquivo especial em /proc/sys/vm/drop_caches. Escrever 3 nele força o kernel a esvaziar o page cache. Precisa root. No nosso teste, usamos entre write e read pra garantir que o read venha do storage de verdade e não da RAM.
ECC (Error Correcting Code)
Esquema de redundância em memórias e storage que detecta e corrige erros de bit. Quando um bit flipa por causa de raios cósmicos ou desgaste, o ECC corrige sem perda. Quando o erro é "uncorrectable", aí teve perda real de dado.
eMMC (embedded MultiMediaCard)
Padrão de chip de armazenamento flash usado em devices entry-level. Velocidade típica: 50-100 MB/s write, 200-300 MB/s read. Comunica via barramento MMC.
Enforcing (modo SELinux)
Modo padrão de SELinux. Bloqueia acessos que violam a policy. Em produção pra cliente final, Android usa Enforcing.
EXT_CSD (Extended Card-Specific Data)
Estrutura de 512 bytes dentro do chip eMMC com metadados detalhados: capacidade, life time A, life time B, pre-EOL, configurações de boot, etc. Lido via comando CMD8 do protocolo MMC. Os bytes 267-269 são life time / pre-EOL.
ext4
Sistema de arquivos Linux padrão. /data em devices Android antigos era ext4. Hoje usa F2FS em devices novos.
F2FS (Flash-Friendly File System)
Sistema de arquivos otimizado pra storage flash (eMMC/UFS). Mais eficiente que ext4 pra padrões de I/O de mobile. Padrão em Android 10+ pra /data.
fastboot
Protocolo/modo de boot do Android usado pra flashar imagens nas partições. Comando fastboot flash <partition> <image.img> grava o arquivo na partição correspondente. Device entra em fastboot via combinação de teclas ou adb reboot bootloader.
getprop
Comando do Android que lê system properties (pares chave=valor preenchidos pelo bootloader/init/build). Ex: getprop ro.product.model retorna o nome do modelo.
HAL (Hardware Abstraction Layer)
Camada do Android que isola o framework Java do hardware específico. Cada vendor implementa seu HAL pra câmera, audio, sensors, etc.
ioctl
Syscall do Linux pra operações específicas em devices que não cabem em read/write padrão. Ex: mmc-utils usa ioctl pra mandar comandos MMC direto pro chip. Geralmente requer privilégios.
JEDEC
Organização que define padrões de memória semicondutora. Especifica o protocolo eMMC, formato do EXT_CSD, etc. Os valores 0x01–0x0B do LifeTime/Pre-EOL vêm da spec JEDEC eMMC.
kernel
Núcleo do sistema operacional. Gerencia processos, memória, drivers de hardware, sistemas de arquivos. O Android usa o kernel Linux.
LifeTime A / LifeTime B
Estimativas de desgaste das células de memória flash, calculadas pelo controlador interno do chip eMMC. A geralmente é SLC (mais resistente, pra metadados), B é MLC/TLC (menos resistente, pra dados). Valores de 0x01 (0-10% usado) até 0x0B (excedido).
LK (Little Kernel)
Bootloader usado em SoCs MediaTek. É quem inicializa o hardware antes do kernel Linux subir. Em MT6761, o LK é quem monta a cmdline do kernel — por isso BOARD_KERNEL_CMDLINE no AOSP não funciona, tem que mexer no project file do LK.
LPDDR (Low Power DDR)
Versão da memória DDR otimizada pra baixo consumo, usada em devices móveis. Versões: LPDDR3 (antiga), LPDDR4/4X (mainstream), LPDDR5/5X (flagship).
MAC (Mandatory Access Control)
Modelo de segurança onde o SO impõe regras independente do dono do arquivo (oposto de DAC). SELinux é uma implementação de MAC.
MD5
Algoritmo de hash que produz um "resumo" de 128 bits de qualquer arquivo. Usado no nosso teste pra comparar bytes antes/depois do write+read — se o hash mudou, dados corromperam. Não é seguro pra criptografia, mas serve pra integridade.
MID (Manufacturer ID)
Bytes do CID do eMMC que identificam o fabricante. Ex: 0x15=Samsung, 0x90=SK Hynix, 0x70=Kingston.
mksh (MirBSD Korn Shell)
Shell padrão do Android (substituto do bash). Acessado via /system/bin/sh. Compatível com a maior parte do POSIX shell, com pequenas diferenças.
mlock
Syscall do Linux que trava uma região de RAM, impedindo o kernel de mover ela pra swap ou reciclar páginas. Usado pelo memtester pra garantir que o teste rode na mesma RAM física do começo ao fim.
MMC
MultiMediaCard. Padrão original de cartões de memória flash. eMMC = versão soldada na placa.
MTK (MediaTek)
Fabricante taiwanês de SoCs (chipsets) pra celulares e tablets, especialmente segmento mid/entry-level. MT6761 (Helio A22) é um SoC MTK usado no Positivo L400.
OOM (Out of Memory)
Situação onde o kernel não tem mais RAM pra alocar. O OOM killer escolhe um processo pra matar e libera RAM. Em dmesg aparece como "killed process X" ou "out of memory".
page cache
Cache de páginas de arquivo em RAM mantido pelo kernel. Acelera leituras repetidas. Pode mascarar problemas em testes de I/O — daí a importância do drop_caches.
Permissive (modo SELinux)
Modo de SELinux que loga violações mas não bloqueia. Usado pra debug/desenvolvimento e (no nosso caso) pra teste de fábrica.
platform_app
Tipo de app Android com privilégios elevados, instalado em /system/priv-app/ ou /product/priv-app/ e assinado com a platform key da imagem. Tem RLIMIT_MEMLOCK=unlimited e acesso a APIs system-level.
PNM (Product Name)
Bytes do CID do eMMC que identificam o modelo do chip, codificados em ASCII. Ex: "FN62" é uma família Samsung KLM.
Pre-EOL (Pre End-of-Life)
Indicador do chip eMMC sobre proximidade do fim de vida. Valores: 0x01 (Normal), 0x02 (Warning ~80% spare consumido), 0x03 (Urgent — spare esgotado).
ProcessBuilder
Classe Java/Kotlin pra criar processos filhos. No nosso APK, usado pra rodar shell scripts: ProcessBuilder("/system/bin/sh", "/path/to/script.sh").
/product (partição)
Partição Android (desde Android 9) onde ficam apps customizados do produto/region. APKs como prebuilt vão em /product/priv-app/. Antes de Android 9, tudo era em /system/priv-app/.
/proc
Sistema de arquivos virtual do Linux que expõe info de processos e do kernel. Ex: /proc/meminfo, /proc/cpuinfo, /proc/PID/status. Não existe no disco — é gerado em memória pelo kernel.
RLIMIT_MEMLOCK
Limite por processo pra quanto de RAM pode ser travada com mlock. Definido baseado no contexto SELinux do processo. untrusted_app tem ~8 MB, platform_app tem unlimited.
RMA (Return Merchandise Authorization)
Processo de devolução de produto defeituoso pelo cliente. Cada RMA custa caro (logística reversa, reposição, perda de reputação). O teste de fábrica existe pra evitar RMAs por defeito de RAM/storage.
SDK (Software Development Kit)
Conjunto de ferramentas pra desenvolver pra uma plataforma. Android SDK inclui adb, fastboot, emulador, libs.
SELinux (Security-Enhanced Linux)
Sistema de segurança MAC que controla acessos baseado em contextos de segurança (não em dono/grupo). Tem 2 modos: Enforcing (bloqueia) e Permissive (só loga).
SLC / MLC / TLC
Tipos de células de memória flash NAND:
  • SLC (Single-Level Cell) — 1 bit por célula, mais rápido e durável, mais caro.
  • MLC (Multi-Level Cell) — 2 bits/célula, balanceado.
  • TLC (Triple-Level Cell) — 3 bits/célula, mais barato e denso, menos durável.
Chips eMMC modernos têm uma mistura — SLC pra área de boot/metadata e TLC pro grosso dos dados.
SoC (System on Chip)
Chip único que integra CPU, GPU, modem, controladores de RAM/storage, etc. Ex: MediaTek MT6761, Spreadtrum SC9863A, Qualcomm Snapdragon 8 Gen 2.
SPRD (Spreadtrum, hoje Unisoc)
Fabricante chinês de SoCs pra mobile. Concorrente direto da MediaTek em segmento entry/mid. Usado nos modelos Positivo TL10 e T2070D.
/sys (sysfs)
Sistema de arquivos virtual que expõe info de hardware e drivers. Ex: /sys/class/mmc_host/... tem todos chips MMC detectados.
system properties
Sistema chave=valor do Android usado pra config global. Lido com getprop, escrito com setprop. Preenchido por bootloader, init, build system e código de runtime.
UFS (Universal Flash Storage)
Padrão moderno de storage flash, sucessor do eMMC, usado em devices high-end. Muito mais rápido (até 1 GB/s). Usa interface serial SCSI em vez do barramento MMC paralelo.
UID (User ID)
Número que identifica um usuário/processo no Unix. UID 0 = root. UID 1000 = system. UID 2000 = shell (usado pelo adb). UIDs 10000+ = apps comuns.
userdebug / user / eng (build types)
Tipos de build do AOSP. user = produção (sem root, sem debug). userdebug = produção com su e debug habilitados. eng = engineering, máximo de logs/tools.
