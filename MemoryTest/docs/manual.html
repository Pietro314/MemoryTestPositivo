MemoryTest

Manual de uso para fábrica e QA

Versão do documento: 2.0 Público: linha de produção, QA, validação Plataforma: Android (factory build com root)

1. Sobre o app

O MemoryTest é uma ferramenta de validação fabril para Android. Roda dois conjuntos de testes nas memórias do device:

  • RAM (memória volátil): usa o memtester para escrever padrões de bits, ler de volta e identificar células defeituosas.
  • Storage (eMMC ou UFS): mede velocidade real de escrita e leitura sequencial via dd, lê o estado de saúde (life time, pre-EOL) reportado pelo controlador da NAND, e valida integridade pós-escrita por hash.
Por que "MemoryTest" se também testa storage? Em fabricação de device móvel, "memory" é jargão para qualquer chip de memória — RAM volátil e storage não-volátil. Ambos são chips de memória soldados na mesma placa, e ambos precisam ser validados antes do device sair da esteira.

O resultado de cada execução é PASS ou FAIL, com log detalhado. Cada device cadastrado tem seus próprios limiares — porque o que é "lento" para UFS 4.0 é absurdamente rápido para eMMC entry, e o que é teste rápido para 4 GB de RAM seria infinito em 16 GB.

2. Fluxo de uso

A tela inicial do app é uma dashboard com 3 cards, cada um representando uma forma de iniciar um teste. Escolha o que se aplica:

  1. Abra o app — cai direto na dashboard.
  2. Escolha um dos 3 fluxos:
    • Teste Default — usa a configuração padrão da fábrica (baixa do servidor local; em falha, cai no Default(T2070D) embutido no APK).
    • Teste Import Dados — identifica o device automaticamente via Build.DEVICE e baixa o JSON específico daquele modelo do servidor (ex: TL10.json).
    • Cadastrar device — fluxo manual antigo: cadastra um novo device informando RAM, storage, classe, etc.
  3. O app abre o detalhe do device e oferece dois testes: Factory (rápido, ~1–3 min) ou Deep RAM (longo, dezenas de minutos a horas).
  4. Aguardar a execução; acompanhar status por seção e log completo.
  5. Ver o resultado: PASS ou FAIL com justificativa, e salvar o relatório se necessário.
Quem só quer rodar um teste rápido — toca em Teste Default ou Teste Import Dados e segue. Não precisa cadastrar nada manualmente. A seção 3 — Dashboard detalha cada fluxo.

3. Dashboard — 3 fluxos de teste

A DashboardActivity é a tela inicial do APK desde a v2.0. Cada card é um caminho diferente até o teste — só muda de onde vem a configuração (parâmetros de RAM, storage, limiares).

3.1 Card "Teste Default"

Atalho para a configuração padrão da fábrica. Bom para teste rápido em qualquer device sem cadastro prévio.

O que acontece em ordem

  1. App tenta baixar default_memtest.json do servidor local (URL configurada em Settings).
  2. Sucesso: persiste a config baixada sobre a linha Default(T2070D) do banco e mostra Snackbar "Configuração baixada do servidor".
  3. Falha de rede / servidor offline / JSON inválido: cai no perfil Default(T2070D) embarcado no APK e mostra Snackbar "Servidor indisponível — usando default embarcado".
  4. Em qualquer caso, abre a tela de detalhe do device com o perfil resolvido — você escolhe FACTORY ou DEEP_RAM e roda.

O perfil "Default(T2070D)" embarcado

Vem semeado no banco do APK no primeiro start. Baseado no MCP Samsung KMDH6001DA-B422: 4 GB LPDDR4X, 64 GB eMMC 5.1. É o fallback quando o servidor não responde.

Não dá pra excluir o Default(T2070D) — bloqueio em 3 camadas (helper isDefaultEmbedded, repositório, e UI esconde o item de delete). Editar é permitido. Quando o JSON do servidor é baixado, sobrescreve os campos dele mantendo o mesmo registro no banco.

3.2 Card "Teste Import Dados"

Detecta automaticamente o modelo do smartphone que está sendo testado e baixa o JSON específico daquele modelo. Útil quando a fábrica testa vários modelos diferentes — cada um tem seus próprios limiares de storage e RAM esperada.

O que acontece em ordem

  1. App lê Build.DEVICE do device atual (ex: TL10, T2070D, M51).
  2. Tenta baixar <Build.DEVICE>.json do servidor local — ex: http://192.168.0.42:8080/TL10.json.
  3. Sucesso: persiste no banco (upsert por marker name+modelCode do JSON) e abre o detalhe daquele perfil. Snackbar: "Configuração de TL10 baixada do servidor".
  4. Falha (404 ou rede): mostra Snackbar "Perfil não encontrado para TL10. Será usado o default (Default(T2070D))" e cai no fluxo do Card 1 — ou seja, ainda roda o teste, mas com a configuração padrão do T2070D em vez de uma específica para o TL10.

Como descobrir o Build.DEVICE de um modelo

adb shell getprop ro.product.device
# Ex: TL10

Esse é o nome do arquivo que você precisa criar no servidor: TL10.json. Veja a seção Convenção de nomes para detalhes.

3.3 Card "Cadastrar device"

Abre o fluxo manual de cadastro (a antiga tela inicial do app). Use quando:

  • Está testando um modelo novo que ainda não tem JSON no servidor.
  • Quer ajustar parâmetros específicos sem mexer no servidor.
  • Está fazendo bancada / RMA com configurações experimentais.

Fluxo idêntico ao detalhado em Cadastro de device.

4. Servidor local de configurações

Os dois primeiros cards da dashboard buscam JSONs num servidor HTTP local na rede Wi-Fi. Não precisa de internet — só de um PC ou notebook na mesma rede que os devices em teste.

Por que ter um servidor

  • Centralizar configs — um lugar só pra ajustar limiares de todos os modelos da fábrica.
  • Sem rebuild do APK — mudar parâmetro vira edição de JSON em texto, salvar, próximo teste já usa o valor novo.
  • Múltiplos modelos — cada modelo tem seu JSON próprio (TL10.json, T2070D.json, …); o APK escolhe automaticamente pelo Build.DEVICE.

Valores válidos para storageClass

String com um dos valores abaixo (sensitive a caixa): EMMC_ENTRY, EMMC_5_0, EMMC_5_1, UFS_2_1, UFS_3_1, UFS_4_0, CUSTOM. Veja a tabela em Storage Class para entender o que cada um significa.

Tolerância do parser

Números podem ser inteiros ("expectedRamGb": 4) ou string ("expectedRamGb": "4") — o parser aceita os dois. Útil quando o servidor serializa tudo como string.

4.3 Subir um servidor local (Mac/Windows)

Qualquer HTTP server estático serve. Mais simples: Python embutido no sistema. Pode ser substituído por nginx/IIS/caddy se precisar de algo mais robusto.

Pré-requisitos

  • PC e celular na mesma rede Wi-Fi.
  • Python 3 instalado (vem nativo no Mac; no Windows, instalar via Microsoft Store ou python.org).
  • Pasta com os arquivos JSON criados (ex: ~/memtest/ ou C:\memtest\).

Mac

# 1. Descobre o IP do Mac na Wi-Fi
ipconfig getifaddr en0
# Ex: 192.168.0.42

# 2. Sobe o servidor na pasta com os JSONs
cd ~/memtest
python3 -m http.server 8080

Windows (PowerShell)

# 1. Descobre o IP da Wi-Fi
(Get-NetIPAddress -InterfaceAlias "Wi-Fi" -AddressFamily IPv4).IPAddress
# Ou rode 'ipconfig' e procure IPv4 do adaptador Wi-Fi

# 2. Sobe o servidor
cd C:\memtest
python -m http.server 8080
Firewall — primeira vez que Python abre porta, o sistema pede permissão. Marque "Redes privadas" e clique Permitir. Mac: System Settings → Network → Firewall → permite Python. Windows: Windows Defender → Permitir aplicativo.

Validar pelo navegador

No celular, abra o navegador e teste: 

http://192.168.0.42:8080/default_memtest.json

Se aparecer o JSON formatado, está tudo OK. Se der erro, ver troubleshoot abaixo.

Troubleshoot

SintomaCausaFix
Browser do celular não abre Firewall do PC bloqueando Liberar Python no firewall (privadas)
Address already in use Porta 8080 ocupada Trocar para 8888 (e ajustar URL no app)
App mostra "usando default embarcado" URL errada nas Settings Conferir preview da URL final na tela Settings
Wi-Fi corporativa bloqueia AP isolation Usar hotspot do celular ou rede de casa

4.4 Configurar a URL no APK (tela Settings)

Para o APK encontrar o servidor, configure a URL base na tela de configurações.

  1. Na dashboard, toque no ícone de engrenagem (canto superior direito).
  2. No campo "URL base do servidor", cole a URL com esquema, IP e porta — terminando em /: 
    http://192.168.0.42:8080/
  3. O preview abaixo do campo mostra em tempo real a URL final que o app vai bater (ex: http://192.168.0.42:8080/default_memtest.json) — confira se é o esperado.
  4. Toque Salvar. A URL fica persistida em SharedPreferences; todas as próximas chamadas usam ela.

Validar via adb (sem abrir o app)

adb shell curl -v http://192.168.0.42:8080/default_memtest.json

Se o curl baixar o JSON, o problema (se houver) está no app. Se nem o curl chegar, é rede/firewall.

5. O que o app testa

5.1 RAM

O memtester aloca uma região de RAM e executa uma bateria de padrões de teste (todos zeros, todos uns, walking ones, walking zeros, XOR patterns, bit flip, etc.). Lê de volta e compara. Qualquer divergência é um bit ruim.

Defeitos típicos que o memtester pega:

  • Bit stuck (sempre 0 ou sempre 1, independente do que foi escrito).
  • Crosstalk (escrita em um endereço afeta o vizinho).
  • Falha intermitente sob padrão específico (refresh, retenção marginal).
  • Endereçamento errado (escrita em A é lida em B).

RAM não tem desgaste. Ou está boa, ou está com defeito. Por isso o teste binariamente passa ou falha — não existe "75% de vida útil de RAM".

5.2 Storage (eMMC / UFS)

O teste de storage tem três partes:

  1. Health check: lê life_time_estimation_a/b (UFS) ou life_time (eMMC) do sysfs. Esses são contadores mantidos pelo próprio controlador do chip — quanto da NAND já foi gasta. Storage novo de fábrica deve reportar 0x01 (0–10% usado). Valor alto em device novo indica chip recondicionado, downgrade fraudulento ou batch antigo.
  2. Velocidade I/O: o dd escreve um arquivo de tamanho configurável em /data, mede o tempo, calcula MB/s. Faz o mesmo para leitura, depois de limpar o cache. Compara com o limiar mínimo do device — se ficar abaixo, FAIL.
  3. Integridade: calcula MD5 do arquivo escrito, força sync, lê de novo, recalcula. Se hashes diferem, há corrupção silenciosa (NAND grava errado, FTL com bug).

6. Cadastro de device — campo a campo

Cada campo do formulário tem uma origem indicada por uma das tags abaixo:

  • METADATA Só identifica o device. Não vai para o script.
  • DATASHEET Vem direto do datasheet do componente.
  • PRESET Sugerido automaticamente quando você seleciona RAM ou Storage Class.
  • POLÍTICA DE TESTE Decisão da fábrica/QA, não do componente. Calibra o rigor.

6.1 Seção "Identificação"

Nome do device METADATA

Cadastro de device → Identificação → Nome do device

O que é
Nome amigável que aparece na lista. Ex: T2070D, Galaxy A15.
De onde tirar
Você escolhe. Use o nome comercial ou interno do device.
Vai para o script?
Não.

Fabricante METADATA

Cadastro de device → Identificação → Fabricante

O que é
Quem produziu o device — ou quem produz o chip de memória, se quiser registrar isso.
De onde tirar
Datasheet do chip (ex: Samsung, SK hynix, Micron) ou do device.
Vai para o script?
Não.

Código do modelo (opcional) METADATA

Cadastro de device → Identificação → Código do modelo (opcional)

Part number do componente / device. Ex: KMDH6001DA-B422, H9HP52ACPMADAR.
De onde tirar
Capa do datasheet (sempre no canto superior).

Notas (opcional) METADATA

Cadastro de device → Identificação → Notas (opcional)

O que é
Campo livre. Use para registrar o batch, observações, link para datasheet, etc.

6.2 Seção "Hardware esperado"

RAM (GB) EXPECTED_RAM_GB DATASHEET

Cadastro de device → Hardware esperado → RAM (GB)

O que é
Quanto de RAM o device deveria ter. Selecionado via dropdown.
O que o script faz
Lê MemTotal do /proc/meminfo. Se a diferença for maior que ~10%, FAIL.
Por que importa
Pega device com chip de RAM faltando, mal soldado, ou com binning errado da fábrica (ex: vendedor mandou 2 GB em vez de 4 GB).
Onde achar no datasheet
Linha "Memory Density" da seção LPDDR. Lembrar conversão 1 byte = 8 bits: 16 Gb = 2 GB, 32 Gb = 4 GB, 64 Gb = 8 GB, 128 Gb = 16 GB.
Efeito de auto-fill
Selecionar a quantidade preenche automaticamente todos os campos da seção "Teste padrão (rápido)" e "Diagnóstico profundo de RAM" com valores sugeridos.
Default se nada for setado
4

Storage (GB) EXPECTED_STORAGE_GB DATASHEET

Cadastro de device → Hardware esperado → Storage (GB)

O que é
Capacidade nominal do storage (eMMC/UFS) em GB.
Onde achar no datasheet
Capa: ex. "64GB e.MMC", "128GB UFS 3.1".
Vai para o script?
Sim, como metadado de validação. Hoje não derruba o teste sozinho, mas é registrado no log.

Classe de storage DATASHEET PRESET

Cadastro de device → Hardware esperado → Classe de storage

O que é
Geração de tecnologia do storage. Selecionado via dropdown. Define a régua de velocidade que o teste vai usar.
Opções
eMMC entry (≤4.5) · eMMC 5.0 · eMMC 5.1 · UFS 2.1 · UFS 3.1 · UFS 4.0 · Personalizado
Onde achar no datasheet
Seção de features. Procure "eMMC Ver. 5.x compatible" ou "UFS 3.x compliant".
Por que precisa selecionar
A diferença de velocidade entre eMMC entry e UFS 4.0 é ~100×. Sem informar a classe, um chip UFS 4.0 com defeito grave passaria no teste, ou um eMMC entry saudável seria reprovado.
Efeito de auto-fill
Selecionar a classe preenche automaticamente os três campos da seção "Limiares de Storage": Velocidade mínima de escrita, Velocidade mínima de leitura e Tamanho do teste de I/O. Veja a tabela em § Storage Class.

6.3 Seção "Limiares de Storage"

Esses três campos definem o que conta como "storage saudável". São auto-preenchidos ao escolher a Classe de storage na seção anterior, mas tudo é editável — você pode apertar ou afrouxar a régua conforme a política da fábrica.

Velocidade mínima de escrita (MB/s) MIN_WRITE_MBPS PRESET POLÍTICA DE TESTE

Cadastro de device → Limiares de Storage → Velocidade mínima de escrita (MB/s)

O que é
Velocidade mínima de escrita sequencial em MB/s para o teste passar.
O que o script faz
Mede com dd if=/dev/urandom of=testfile bs=4M count=N conv=fsync. Se a velocidade medida for menor que este valor, FAIL.
Como o valor é definido
~50% do throughput sustentado nominal de cada classe. É proposital: dá folga para variação normal de fábrica, mas pega NAND defeituosa, controlador ruim ou downgrade fraudulento (UFS 3.1 sendo entregue com performance de 2.1).
Default se nada for setado
50 (assume eMMC 5.1).

Velocidade mínima de leitura (MB/s) MIN_READ_MBPS PRESET POLÍTICA DE TESTE

Cadastro de device → Limiares de Storage → Velocidade mínima de leitura (MB/s)

O que é
Velocidade mínima de leitura sequencial em MB/s.
O que o script faz
Mede com dd if=testfile of=/dev/null bs=4M depois de limpar o cache (echo 3 > /proc/sys/vm/drop_caches). Compara com este valor.
Default se nada for setado
100

Tamanho do teste de I/O (MB) STORAGE_TEST_SIZE_MB PRESET POLÍTICA DE TESTE

Cadastro de device → Limiares de Storage → Tamanho do teste de I/O (MB)

O que é
Tamanho (em MB) do arquivo escrito e lido para medir velocidade.
Por que importa
Muito pequeno → fica todo no cache de RAM e mede velocidade da RAM, não do storage. Falsa medição otimista.
Muito grande → demora demais na linha de produção. Em UFS 4.0, 256 MB cabem inteiros no WriteBooster SLC e mascaram a NAND real.
Default se nada for setado
512

6.4 Seção "Teste padrão (rápido)"

Este conjunto de campos controla o teste de RAM rápido, usado na esteira de produção. Objetivo: ~30–90s, suficiente para pegar defeito grosseiro sem travar a linha. Auto-preenchidos ao escolher a quantidade de RAM na seção "Hardware esperado".

% da RAM disponível QUICK_MEMTEST_PERCENT PRESET

Cadastro de device → Teste padrão (rápido) → % da RAM disponível

O que é
Quantos por cento da RAM livre (não da total) o memtester vai usar.
Por que % e não MB fixo
RAM livre varia entre devices e momentos (Android usa cache agressivo). Pegar uma fração é mais robusto.
Por que cai em devices grandes
O memtester é não-linear no tempo. Em 16 GB, testar 50% (8 GB) levaria horas. Por isso devices grandes recebem % menor.
Default
40

Máximo testado (MB) QUICK_MEMTEST_MAX_MB PRESET

Cadastro de device → Teste padrão (rápido) → Máximo testado (MB)

O que é
Limite superior. Mesmo que % da RAM disponível × RAM livre dê um valor maior, o memtester nunca vai usar mais que isso.
Por que existe
Trava de segurança contra OOM em devices que reportam muita RAM livre, e contra tempo de teste explodir.
Default
512

Mínimo testado (MB) QUICK_MEMTEST_MIN_MB PRESET

Cadastro de device → Teste padrão (rápido) → Mínimo testado (MB)

O que é
Limite inferior. Se % da RAM disponível × RAM livre der menos que isso, o memtester usa esse mínimo.
Por que existe
Abaixo de ~64–128 MB o memtester não exercita o subsistema de cache/MMU adequadamente — RAM ruim pode passar batido.
Default
128

Loops do memtester QUICK_MEMTEST_LOOPS PRESET

Cadastro de device → Teste padrão (rápido) → Loops do memtester

O que é
Quantas vezes o memtester repete a bateria completa de padrões.
Recomendação
Sempre 1 no teste padrão. Linha de produção não tem tempo para 2 voltas, e uma única volta pega defeito grosseiro com ótima taxa.
Default
1

Timeout (segundos) QUICK_MEMTEST_TIMEOUT_S PRESET

Cadastro de device → Teste padrão (rápido) → Timeout (segundos)

O que é
Watchdog. Se o memtester não terminar em N segundos, o script o mata e marca FAIL.
Por que existe
RAM ruim pode causar hang. Sem timeout, a esteira de produção fica parada esperando.
Default
600 (10 min)

6.5 Seção "Diagnóstico profundo de RAM"

Versão pesada do teste de RAM. Não é para linha — é para diagnóstico de bancada, RMA, validação de troca de chip. Usa mais RAM, mais voltas, mais tempo. Os campos têm o mesmo significado dos da seção anterior, com valores mais agressivos. Auto-preenchidos ao escolher a quantidade de RAM na seção "Hardware esperado".

% da RAM disponível MEMTEST_PERCENT PRESET

Cadastro de device → Diagnóstico profundo de RAM → % da RAM disponível

O que é
Mesmo conceito do teste padrão, porém valores maiores. O diagnóstico profundo usa mais RAM para pegar defeitos sutis.
Faixa típica
25–60% (vs 15–50% do teste padrão).
Default
60

Máximo testado (MB) MEMTEST_MAX_MB PRESET

Cadastro de device → Diagnóstico profundo de RAM → Máximo testado (MB)

O que é
Teto absoluto de RAM testada no diagnóstico profundo.
Faixa típica
512–4096 MB. Em devices a partir de 2 GB, normalmente 4096 MB (limite prático do memtester antes de fragmentação).
Default
2048

Mínimo testado (MB) MIN_MEMTEST_MB PRESET

Cadastro de device → Diagnóstico profundo de RAM → Mínimo testado (MB)

O que é
Piso mínimo de RAM testada — abaixo disso o memtester não exercita o cache/MMU adequadamente.
Default
128

Loops do memtester MEMTEST_LOOPS PRESET

Cadastro de device → Diagnóstico profundo de RAM → Loops do memtester

O que é
Quantas voltas completas. Mais voltas = mais chance de pegar defeito intermitente.
Recomendação
3 voltas em devices com até 6 GB. 2 voltas em devices maiores (8 GB+) — mais voltas levaria horas.
Default
3

Timeout (segundos) MEMTEST_TIMEOUT_S PRESET

Cadastro de device → Diagnóstico profundo de RAM → Timeout (segundos)

O que é
Watchdog do diagnóstico profundo. Bem maior que o teste padrão.
Faixa típica
1200 s (20 min) em 1 GB → 7800 s (~2 h) em 18 GB. Calibrado por RAM × loops.

7. Auto-preenchimento e edição livre

Princípio: selecionar RAM ou Storage Class é uma sugestão. O app preenche valores razoáveis, mas todos os campos continuam editáveis.

O que dispara o auto-fill

  • Selecionar a quantidade de RAM → preenche todos os QUICK_MEMTEST_* e MEMTEST_* (deep) com o preset daquele tier.
  • Selecionar a Storage Class → preenche MIN_WRITE_MBPS, MIN_READ_MBPS e STORAGE_TEST_SIZE_MB.
  • Existir outro device cadastrado com a mesma quantidade de RAM → o app oferece "copiar configuração" desse device. Útil quando você ajustou valores num device e quer replicar em outros do mesmo tier.

Quando ajustar manualmente

  • Storage industrial / pSLC / SLC: aguenta velocidades menores. Reduza MIN_WRITE_MBPS e MIN_READ_MBPS.
  • Storage com WriteBooster muito grande (UFS 3.1+): aumente STORAGE_TEST_SIZE_MB para sair do cache SLC.
  • RAM com timing apertado / overclock: aumentar QUICK_MEMTEST_LOOPS para 2 pode ajudar a flagrar instabilidade térmica.
  • Esteira muito apertada: reduzir QUICK_MEMTEST_PERCENT para cortar tempo, ciente da menor cobertura.

Snapshot — importante

Os valores são salvos como snapshot no device. Se o app for atualizado e os presets mudarem, os devices já cadastrados não recebem os valores novos automaticamente. Para repropagar, abra o device, reselecione RAM ou Storage Class, e salve.

9. Datasheet × app

Nem todo campo do app sai do datasheet do componente. Datasheet descreve o que o chip é; parâmetros de teste descrevem como você vai testá-lo. Isso é decisão de fábrica/QA, não do fabricante do chip.

9.1 O que vem do datasheet

  • Fabricante — capa / rodapé do PDF.
  • Modelo / Part Number — capa.
  • RAM (GB) — seção LPDDR, "Memory Density per die" × número de dies. Lembrar conversão Gb→GB.
  • Storage (GB) — capa: "NN GB e.MMC" ou "NN GB UFS".
  • Storage Class — seção features: "eMMC Ver. 5.x" ou "UFS x.x".

9.2 O que NÃO vem do datasheet

  • MIN_WRITE_MBPS / MIN_READ_MBPS — datasheet dá pico teórico (ex: HS400 = 400 MB/s), não o limiar de PASS/FAIL. O limiar é decisão de QA: ~50% do sustentado.
  • STORAGE_TEST_SIZE_MB — parâmetro de teste, não do chip.
  • QUICK_MEMTEST_* e MEMTEST_* — política de quanto e por quanto tempo testar. Vem da decisão de fábrica/QA.

9.3 Exemplo prático — KMDH6001DA-B422

Tomando o datasheet do MCP Samsung KMDH6001DA-B422 (T2070D), ponto a ponto:

10. Como ler um datasheet de memória

Datasheet de chip de memória normalmente tem 100–300 páginas. Para o cadastro no app, você só precisa olhar:

Página 1 — capa

Sempre tem:

  • Nome do fabricante (Samsung, SK hynix, Micron, Kingston…).
  • Part number completo (ex. KMDH6001DA-B422).

Seção 1.0 / "Features"

Em torno da página 2–4. Procure:

  • "embedded MultiMediaCard Ver. X.Y" → Storage Class é eMMC X.Y.
  • "UFS Version X.Y compliant" ou "HS-Gear N" → UFS, ver tabela abaixo:
    Versão UFSHS-Gear típico

11. Sem datasheet — descobrir no próprio device

Se você tem o device em mãos mas não tem datasheet, dá para descobrir tudo via shell. Conecte por adb com o device em modo desenvolvedor:

RAM total

adb shell cat /proc/meminfo | head -1
# MemTotal:        3893632 kB
# 3893632 / 1024 / 1024 ≈ 4 GB → arredondar para o próximo valor "comercial" (4 GB)

Tipo de LPDDR

adb shell getprop ro.boot.ddr_type
adb shell getprop ro.boot.dram_type
adb shell getprop vendor.boot.ddr_type
# Resposta típica: "LPDDR4X", "LPDDR5", "LPDDR3"

Storage — capacidade e versão

# UFS:
adb shell cat /sys/class/scsi_host/host*/proc_name
adb shell cat /sys/class/scsi_device/*/device/vendor /sys/class/scsi_device/*/device/model
adb shell cat /sys/class/scsi_device/*/device/rev   # versao UFS

# eMMC:
adb shell cat /sys/block/mmcblk*/device/type
adb shell cat /sys/block/mmcblk*/device/cid    # CID com manufacturer e modelo
adb shell cat /sys/block/mmcblk*/device/csd    # contem version
adb shell cat /sys/block/mmcblk*/device/ext_csd # detalhado (so root)

Tamanho de storage

adb shell df -h /data
adb shell blockdev --getsize64 /dev/block/mmcblk0    # bytes totais

12. Executar um teste

  1. Na tela inicial, toque no device cadastrado.
  2. Escolha:
    • Factory — quick RAM + storage. Use na linha de produção.
    • Deep RAM — só RAM, vários loops. Use em bancada/RMA.
  3. Toque "Iniciar". A tela mostra:
    • Aba "Status" — cards das seções com PASS / RUNNING / FAIL.
    • Aba "Log" — saída completa do script em tempo real.
  4. No fim, o app salva o relatório em /sdcard/MemoryTest/ (ou no filesDir interno se não tiver permissão), e a execução fica registrada no histórico.

Lendo o resultado

13. Glossário

eMMC (embedded MultiMediaCard)

Chip de NAND flash + controlador embarcado, soldado na placa do device. Sucessor do MMC. Tem versões 4.5, 5.0 e 5.1, com velocidades crescentes (HS200, HS400). Padrão JEDEC.

UFS (Universal Flash Storage)

Sucessor do eMMC, com interface serial full-duplex (comando e dado simultâneos). Significativamente mais rápido. Versões principais: 2.1, 3.1, 4.0. Padrão JEDEC.

JEDEC

Organização de padronização da indústria de semicondutores. Define oficialmente as specs de eMMC, UFS, LPDDR.

NAND flash

Tipo de memória não-volátil usado em todo storage de smartphone. Tem ciclos de escrita finitos (P/E cycles). O controlador eMMC/UFS faz wear leveling e bad block management para esticar a vida útil.

LPDDR (Low-Power Double Data Rate)

Família de RAM dinâmica para mobile. LPDDR3, 4, 4X, 5, 5X. Cada geração ~2× mais rápida e mais eficiente que a anterior.

memtester

Programa Linux que aloca uma região de RAM e roda padrões de teste para detectar células defeituosas. Em uso desde os anos 90, agora portado para Android.

dd

Utilitário Unix de cópia byte a byte. Usado no script para escrever um arquivo de tamanho conhecido e medir o tempo, calculando MB/s.

Sustained throughput

Velocidade que o storage consegue sustentar continuamente, depois do cache encher. Tipicamente 30–60% do pico anunciado pelo fabricante.

Life time / Pre-EOL

Contadores que o controlador de eMMC/UFS expõe via sysfs, indicando quanto da NAND já foi gasta. Em chip novo deve ser 0x01 (0–10% gasto). Valor alto em device de fábrica é red flag.

WriteBooster (UFS 3.1+)

Cache SLC dentro do próprio UFS. Aceita escritas em alta velocidade, depois move para a NAND TLC. Para o teste de fábrica, isso pode mascarar performance real — daí o tamanho de teste maior em UFS 3.1+.

SLC / TLC / QLC

Quantos bits cabem por célula NAND. SLC = 1 bit (mais rápido, mais durável, mais caro). TLC = 3 bits (padrão moderno). QLC = 4 bits (mais barato, menos durável). pSLC = TLC operando em modo SLC para ganhar durabilidade.

Snapshot (no contexto do app)

Os valores aplicados ao device no momento do cadastro são "fotografados" e salvos no banco. Mudanças posteriores nos presets do app não retroagem para devices já cadastrados — protege contra surpresa em produção.

14. FAQ — perguntas comuns

Como descobrir qual nome de arquivo o "Teste Import Dados" vai procurar?

O nome é o valor de Build.DEVICE do device, com extensão .json. Para descobrir, ligue o device no PC e rode: 

adb shell getprop ro.product.device

O retorno é exatamente o que o app vai procurar. Ex: se retornar TL10, crie TL10.json no servidor.

O JSON do servidor pode ter campos a mais ou a menos?

A menos: sim. Campos ausentes herdam do perfil Default(T2070D) embarcado. Útil quando você só quer sobrescrever 1–2 limiares e deixar o resto padrão.
A mais: também. Chaves desconhecidas são ignoradas silenciosamente — você pode incluir campos extras (ex: "_comment") sem quebrar o parser.

O que acontece se eu rodar o "Teste Import Dados" e o JSON não existir no servidor?

O app mostra Snackbar avisando "Perfil não encontrado para [Build.DEVICE]. Será usado o default (Default(T2070D))" e cai no fluxo do "Teste Default" — ou seja, ainda roda o teste, mas com a configuração padrão do T2070D em vez de uma específica para aquele device. O técnico pode então criar o JSON correto no servidor e tentar de novo.

Posso cadastrar manualmente um device que também tem JSON no servidor?

Pode. Mas se você usar Teste Import Dados depois, o app faz upsert pelo marker name+modelCode do JSON — se bater com o registro manual, sobrescreve. Se for diferente, cria entrada separada. Recomendação: pra um mesmo modelo, use só um caminho (ou manual, ou via servidor) para evitar confusão no histórico.

Por que o servidor é só HTTP (sem HTTPS)?

É factory test em rede local controlada. HTTPS exigiria certificado válido em cada PC de fábrica — overhead sem benefício real, já que a rede é interna. O Manifest do APK declara android:usesCleartextTraffic="true" exatamente por isso. Se algum dia for usar fora de fábrica, revisar.

Por que existe dropdown de RAM e Storage Class? Não dá para detectar automático?

Daria, parcialmente — via /proc/meminfo para RAM e sysfs para storage. Mas detecção automática é frágil em vendor exótico, e em cenário de fábrica preferimos confiar no que o operador sabe sobre o device que está testando, não em adivinhação. A informação está no datasheet; o operador apenas a confirma.

Editei o preset (no código), mas devices já cadastrados não mudaram. É bug?

Não. Os valores são salvos como snapshot no momento do cadastro. Para repropagar, abra cada device, reselecione RAM/Storage Class, e salve. Esse comportamento é proposital — evita surpresa em produção quando o app é atualizado.

Device falhou no teste de storage por 5 MB/s abaixo do limite. É chip ruim?

Provavelmente não. 5 MB/s pode ser variação térmica, fragmentação do /data, ou cache do kernel não totalmente limpo. Re-rode o teste — se passar, é variação normal. Se falhar consistentemente em múltiplas amostras, é um problema real (chip, controlador, ou solda).

Por que limiares são "só" ~50% do nominal? Não deveriam ser ~80%?

50% pega defeito real (NAND ruim, downgrade fraudulento) sem rejeitar variação normal. 80% rejeitaria devices saudáveis em condições não-ideais (térmica, fragmentação, sample variation), gerando muito falso-positivo e custo de RMA desnecessário. Se a sua aplicação tem requisito mais alto (datacenter, automotivo), edite manualmente.

O memtester pode passar mesmo com RAM ruim?

É raro mas possível. Memtester testa padrões clássicos; se o defeito for em endereço/timing muito específico, pode escapar. Por isso o deep test roda 3 voltas — repetição aumenta a chance de pegar defeito intermitente. Se suspeitar de RAM marginal e quick passar, rode o deep.

STORAGE_TEST_SIZE_MB muito grande está estourando o /data. O que fazer?

O script verifica espaço livre antes de testar e marca SKIP se não couber. Se está estourando mesmo assim, reduza STORAGE_TEST_SIZE_MB no cadastro do device, ou libere espaço no /data (factory build deveria ter /data quase vazio).

Por que o teste exige root?

Para ler life_time de UFS/eMMC (sysfs protegido), limpar drop_caches, e algumas operações de medição precisas. Em factory build (userdebug/eng) o root é fornecido por um daemon nativo embarcado pelo AOSP via init.rc — o app comunica com ele via socket Unix. Em build de usuário comum (user), não roda.

Posso usar este app em produção (não-fábrica)?

Não é o caso de uso. Em build de usuário comum, sem o daemon root, o app não consegue rodar os testes — falha imediato. É uma ferramenta de fábrica e bancada, não de campo.
